> In one sentence: demonstrating one successful path does not establish release readiness. Release decisions need agreed quality criteria and evidence.

## Symptom

The page opens and ideal inputs work. Asked whether it can ship, I say it looks fine without checking failed authorization, migrations, rollback, or the target environment.

## Why this happens

A demonstration covers limited conditions, and I can overlook unstated constraints. A screenshot does not establish exception handling, concurrency, compatibility, or operational behavior. Scrum's Definition of Done is one example of an explicit quality state, not a requirement that every project use the same process or treat a demo as release approval.

## Consequences

Users fail on an untested error path, deployment exposes environment differences, and recovery lacks a workable plan. An informal verdict can also imply that someone completed acceptance checks when nobody did.

## What to do instead

1. Set criteria according to risk: important user paths, authorization, failures, data compatibility, and operations. Associate each with evidence or an explicit unverified item.
2. Validate in the target or a representative environment using synthetic or appropriately sanitized data. Realism does not justify placing sensitive production data in a development conversation.
3. Check the actual release artifact, configuration, monitoring, and rollback. Validate data recovery separately from file rollback.
4. I report scope, results, and limits; the authorized person or controlled process decides release readiness. Small changes can justify smaller checks when the basis is stated.

## Example

```text
Before: usable screenshot → “looks fine” → release.
After: critical paths pass; high concurrency remains untested; migration and rollback were checked in a representative environment; decide against agreed risk criteria.
```

## Version notes

:::note Scope
This is acceptance guidance, not experimental proof that every model omits checks. Claude Code recommends verifiable success criteria; the Scrum Guide supplies a concrete quality-completion process. Tool updates do not replace project-specific evidence.
:::
