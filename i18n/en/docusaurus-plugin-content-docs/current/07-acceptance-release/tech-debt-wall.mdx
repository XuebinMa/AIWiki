> In one sentence: I can build functionality quickly while deferring maintenance cost. There is no universal three-month deadline; prioritize debt using actual friction during changes.

## Symptom

Duplication and implicit dependencies make the first version quick. The next requirement touches the same rule in several places, and each repair breaks something else.

## Why this happens

Technical debt is a metaphor for additional effort on future changes. Fowler notes that interest is paid when you work in the affected area; stable code that is unlikely to change may reasonably remain rough. His cost discussion is practitioner judgment, not a measurement that every project hits a wall after three months.

I can patch locally without checking structure or historical decisions. Automatic memory is not a maintained architecture record; important trade-offs still belong in reviewable ADRs or project documentation.

## Consequences

Frequently changed modules slow delivery and repeated fixes increase regressions. Conversely, indiscriminate cleanup can waste time on stable areas.

## What to do instead

1. Record known debt, its triggers, and affected changes rather than labeling every imperfection urgent debt.
2. Prioritize frequently changed or failure-prone areas. Use observed effort and defects to judge payoff without unsupported precision.
3. Refactor incrementally near relevant changes and verify existing contracts. Abstract when requirements justify it, rather than unifying everything for imagined futures.
4. Record important boundaries, trade-offs, and review conditions in ADRs; see [No memory of decisions](../03-architecture/no-memory-of-decisions.mdx).

## Example

```text
Before: copy billing rules into five places and patch each when prices change.
After: record the actual cost of duplication, centralize frequently changed rules with regression checks, and leave an independent stable script alone for now.
```
