> In one sentence: I can omit authorization, input handling, or secrets controls. Working functionality does not establish security; explicit requirements, automated checks, and review must work together.

## Symptom

Source contains hardcoded keys, queries concatenate external input, or error responses and logs include tokens. Happy paths pass while authorization failures and sensitive-data paths remain unchecked.

GitGuardian's 2026 report observed a 3.2% secret-detection rate for identified Claude Code-assisted commits on public GitHub against a 1.5% baseline. This is an association under a particular identification method, not a measurement of every AI commit or evidence that the tool caused disclosure.

## Why this happens

I can miss security requirements, and existing code can supply unsafe examples. That does not establish that all models cannot recognize secrets or never check security proactively. Normal-function tests alone rarely establish rejection of unauthorized access or data transfers.

Current GitHub push protection covers supported partner, generic, and custom patterns, with some AI secret detection in preview. Availability and blocking depend on type, plan, and configuration; arbitrary secrets are not all detectable.

## Consequences

Credentials can reach unintended readers, services can receive unauthorized calls, and sensitive information spreads through logging or monitoring. A private-repository commit is not automatically a public leak, but exposure must be assessed against actual access and credentials rotated promptly.

## What to do instead

1. Specify object-level authorization, parameterized queries, output encoding, and sensitive-field handling; check rejection paths.
2. Inject credentials through controlled secrets services or environments. Environment variables and `.gitignore` alone do not isolate access.
3. Configure local checks, push protection, and repository scanning. A blocked push does not remove a secret from local history. Restrict bypass permissions and approvals too.
4. Revoke or rotate potentially exposed credentials before cleaning history and downstream copies. Deleting one line in the latest file is insufficient.
5. Inspect logs and exception content: `log.exception` includes exception details and stack traces; it does not automatically redact them.

## Example

```text
Before: return the complete payment exception to the client and log it unchanged.
After: return a generic error plus correlation ID; log reviewed minimal fields without tokens, full request bodies, or unsanitized exception text.
```
