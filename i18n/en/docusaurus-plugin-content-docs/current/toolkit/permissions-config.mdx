> In one sentence: This is a starting point for interactive approvals in Claude Code. It intercepts matching tool calls; actual file and network isolation also depends on the sandbox, credentials, and MCP boundaries. Check your permission mode before copying it.

## Template

```json
{
  "permissions": {
    "deny": [
      "Read(.env)",
      "Read(.env.*)",
      "Read(secrets/**)",
      "Bash(rm *)",
      "Bash(sudo *)",
      "Bash(dropdb *)"
    ],
    "ask": [
      "Edit",
      "Write",
      "Bash(git branch *)",
      "Bash(git commit *)",
      "Bash(git push *)",
      "Bash(git reset *)",
      "Bash(npm *)",
      "Bash(pnpm *)",
      "Bash(npx *)"
    ],
    "allow": [
      "Read",
      "Glob",
      "Grep",
      "Bash(pwd)",
      "Bash(git status)",
      "Bash(git diff)"
    ]
  }
}
```

## How to use it

Place it in the project's `.claude/settings.json`, or adapt it for personal settings using the current documentation. Matching `deny` rules take precedence over `ask`, then `allow`; permission modes, managed policies, and sandbox settings also affect the result.

- **Inspect what a command does.** `git branch` can list branches, delete them, or reset their pointers, so this template asks for that whole family. Tests, lint, and builds can execute repository scripts, read credentials, or use the network. Review scripts and dependencies before deciding whether to pre-approve them for a task.
- **Deny rules have a scope.** `Bash(rm *)` blocks matching forms, not every executable path, shell wrapper, or indirect subprocess. `Read` rules do not surround arbitrary scripts' file access either. A command deny list cannot replace OS isolation.
- **Restrict data and egress separately.** Avoid mounting sensitive files or injecting credentials. Restrict egress in an environment that covers the relevant processes. Claude Code's shell sandbox excludes MCP, hooks, and built-in file/web tools; see [sandbox isolation](../00-setup-collaboration/sandbox-filesystem-isolation.mdx) and [network egress control](../00-setup-collaboration/network-egress-control.mdx).
- **Verify the boundary.** With dummy files containing no real secrets, check ordinary reads, protected paths, branch deletion, and unapproved scripts. A configuration that parses is not enough evidence.

## Applicability boundaries

### When to use it

- Local collaboration where writes, version-control changes, and repository scripts retain interactive approval.
- Teams that need an adaptable, verifiable starting point for permissions.

### When not to use it

- As a complete policy for unattended execution or preventing exfiltration.
- As a configuration to copy unchanged into another tool or permission mode.

### What to replace before use

- Use your real sensitive paths, package manager, and commands; review existing allow rules.
- Check which processes are covered by filesystem, environment, network, MCP, and hook controls.
- Verify current rule syntax and modes with the dummy-data checks above.
