> In one sentence: a tool timeout means I did not receive a result, not that the remote operation never ran. Resuming a long task requires durable records, external-state checks, and an idempotency contract for retryable writes. Treating “continue” as “start over” can duplicate creations, notifications, or completed work.

## Symptom

I generate exports for you. The service accepts a job, but its response is lost. You see a timeout and say “try again.” I create another job, which also succeeds. You receive two results, and the backend charges for both.

The same problem appears across coding sessions: the previous session completed a migration; the new session sees a vague summary and runs it again. The conversation lacks a success message, but the system already has the side effect.

## Why this happens

**Conversation state, task state, and external side effects are different things.** My context can describe what I planned; the remote service knows whether a write occurred. A timeout makes the result unknown. It does not turn it into a failure with no side effects. Amazon's idempotent API engineering article addresses this uncertainty window.

Anthropic's long-running-agent work uses progress artifacts to help later sessions resume. MCP Tasks defines queryable task state machines with deferred result retrieval. Neither alone proves that your business write happens only once. **Combining durable records, queries, and idempotency below is an engineering inference, not a guarantee those sources make about every product.**

Even after recording “about to send,” a process can crash after the remote operation completes but before local success is saved. Closing that gap requires the service's deduplication semantics, transactions, or reliable reconciliation. Rereading the conversation cannot supply them.

## Consequences

- Retrying can duplicate resources, notifications, or orders; later cancellation may not retract information already sent.
- Replayed steps can overwrite completed work and leave later steps with the wrong starting state.
- Sending a cancellation request can be mistaken for rollback while side effects are still completing.
- A new session can reuse expired credentials or old authorization as though resumption were permanent permission.

## What to do instead

Record business-step state rather than keeping only a prose summary:

```text
task_id / step_id: stable local identifiers
operation_key: unchanged when retrying the same business intent, not regenerated each time
request_digest: prevent reuse of one key with different parameters
state: not started / running / succeeded / failed / outcome unknown / cancelled
remote_id / evidence: remote identifier, query result, or completion receipt
next_action: safe retry / query remote state first / human reconciliation needed
```

Persist intent before an external write. If the outcome is unknown, query by the remote task ID or business key first. Where supported, retry within the service's documented key scope, lifetime, and parameter contract. **Generating a local key does not make a service without deduplication idempotent.** For irreversible writes that cannot be queried or deduplicated, request human reconciliation instead of replaying blindly.

On resumption, reconcile current code, remote outcomes, and remaining authorization before choosing the next step. Verify state after cancellation; cancelling a task does not undo completed side effects. Handoff logs should retain necessary identifiers without copying sensitive request bodies unnecessarily.

## Example

**Before:**

```text
create_export times out → new session reruns create_export → two exports exist.
```

**After:**

```text
Persist step intent and business key → call service → response lost; mark outcome unknown.
Resume: query using the existing remote identifier or business key; retrieve completed output.
If retrying, verify deduplication semantics and reuse the key. Without them, stop irreversible
replay for human reconciliation. Save verifiable remote completion before the next step.
```

This is a state-transition sketch. Fields, transaction boundaries, and failure handling must match the actual service.

### Runnable lost-response recovery

From the repository root, without installing dependencies:

```bash
node examples/retry/demo.mjs
```

Use Node.js 22.13 or later in the 22.x line, or Node.js 24+. The [complete example](https://github.com/XuebinMa/AIWiki/blob/main/examples/README.md) first saves the business key, request digest, and budget. The simulated service completes an export, then loses the response and exits the caller. A new process reads the checkpoint, queries the service using the original key, and retrieves the successful result. Assertions check that only one export exists, changed parameters are rejected under the same key, permanent errors are not retried, and restarts do not reset the budget.

The service ledger and caller checkpoint are separate temporary files. Short waits illustrate backoff. This is a single-writer teaching implementation with no real export service or MCP Tasks implementation; it does not establish concurrency, power-loss, or production exactly-once guarantees.

## How this differs from neighboring pitfalls

[Runaway agent loops](./runaway-agent-loops.mdx) concerns missing stop conditions and wasted budget. One retry can cause a duplicate write here. [Git hygiene](./git-hygiene.mdx) protects code changes; it cannot retract a sent notification or remote business object. Checkpoints answer where to continue; idempotency answers whether repetition causes another effect.

## When the exception applies

Retries can be simple for reads or verified idempotent state-setting on one object. A small task with no external side effects also needs no separate task system. The operation's contract must actually support that judgment: identical parameters need not mean identical business intent.

## Version notes

:::note Applicable versions
Sources verified on 2026-10-29. The Tasks page for MCP 2025-11-25 still marks the feature experimental. Support must be negotiated; do not assume any client or tool can resume. Task IDs, polling, and deferred results do not guarantee business-level exactly-once effects. This entry does not claim all coding agents implement durable tasks, automatic recovery, or idempotent writes.
:::

The 2025-11-25 Tasks page describes that historical experimental version. MCP 2026-07-28 moves Tasks into the official `io.modelcontextprotocol/tasks` extension, with its own capability and state handling. Check the protocol version and support on both sides; neither revision supplies business-level exactly-once execution.
