> In one sentence: Mixed tasks may cause me to reuse stale assumptions and add context cost; preserve goals and verified state before continuing, summarizing, or separating sessions, without treating context clearing as file rollback.

## Symptom

I see conversations like this all the time: you ask me to fix an error in the login endpoint, and we fix it. Then you remember something and casually ask, "Oh, by the way, how would you write this regex?" A while later you come back: "About that login thing—can you add some logging?"

Three unrelated things in one conversation. By the third, you'll feel my responses get noticeably duller: I start ignoring conventions you set earlier, or I wrongly drag the regex context into the login code.

## Why this happens

Unrelated discussion can consume context, add processing cost, or transfer assumptions from one task into another. But not all raw history stays in the window forever: clients can trim tool output, summarize history, retrieve on demand, or use separate contexts.

Current Claude Code guidance still recommends clearing between unrelated tasks, while noting that automatic compaction and larger windows change older capacity-management habits. Mixed tasks pose a quality/cost risk to observe, not a law that three topics necessarily degrade an answer.

I should preserve the active goal, verified facts, and unfinished work before choosing to continue, summarize, or start a separate session rather than clearing useful state mechanically.

## Consequences

- I start ignoring instructions you gave earlier, because they're buried under unrelated material.
- I may wrongly carry details from one task into another.
- To correct the drift, you add even more conversation—which crowds the window further. A vicious cycle.

## What to do instead

- **Prefer a separate session for unrelated work.** Preserve progress, the current diff, verification results, and next steps first. Related small questions need not be split mechanically.
- **Rebuild necessary state when returning.** Read current files and the checklist instead of relying only on the previous conversation.
- **Understand /clear before using it.** In current Claude Code it clears conversation context, not disk changes or necessarily rules/memory. Save a checked handoff summary first when work must continue.

## Example

**Before (one conversation):**

```text
You: fix the null pointer error in login()
Me: (fixes it)
You: also, write me a regex that matches emails
Me: (gives the regex)
You: ok, back to login—add failure logging
Me: (cobbles things together in login, occasionally dragging in the email regex)
```

**After:**

```text
You: fix the null pointer error in login()
Me: (fixes it)
You: /clear
You: write me a regex that matches emails
Me: (gives the regex, cleanly)
You: /clear
You: add structured logging to login()'s failure branch
Me: (focused, accurate)
```
