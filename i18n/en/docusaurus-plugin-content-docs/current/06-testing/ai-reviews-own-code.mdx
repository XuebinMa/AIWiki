> In one sentence: My self-review can find problems without proving the code correct. Distinguish same-session self-evaluation, review in fresh context, and external verification. Different models can share errors too; findings need triggers, evidence, and validation.

## Symptom

I finish an authorization filter and you ask for a bug check. I retain my implementation assumptions and miss cross-tenant access. A fresh review may find it or miss it again; LGTM alone does not tell you which happened.

## Why this happens

An authoring session carries assumptions and explanations from implementation. *LLM Evaluators Recognize and Favor Their Own Generations* observed self-preference in its tested models and evaluation tasks and studied its relationship with self-recognition.

That is a warning about evaluation independence, not proof that all code-review blind spots overlap completely or that more capable models must prefer themselves more. Tasks, prompts, context, tools, and models affect results. A fresh review by the same model can still add value.

## Consequences

- Self-evaluation becomes a supposedly independent acceptance gate while correlated errors pass.
- Switching models is mistaken for independent proof, ignoring shared training and assumptions.
- Demanding a fixed number of bugs produces false positives and unnecessary edits.

## What to do instead

**Require a trigger and evidence for each finding, then validate it externally.**

1. Choose fresh context, human review, or another model according to risk. Different models are no guarantee, and minor changes need not accumulate reviewers.
2. Supply requirements, diff, relevant code, and callers; see [diff-only review](./context-starved-review.mdx). The author's “already proven correct” narrative cannot replace evidence.
3. Each finding should identify conditions, impact, location, and reproduction. Mark unconfirmed concerns as such; do not require a quota.
4. Validate with a [test loop](./tests-as-verification-loop.mdx), type checks, static analysis, and necessary human review. Check test assertions and coverage too: green does not establish complete acceptance; see [trust, then verify](./trust-then-verify.mdx).

## Example

**Before:**

```text
Me: The authorization filter is finished.
You: Review it yourself.
Me: Clear structure, no issues, ready to merge.
```

**After:**

```text
Fresh review: Read the authorization contract, diff, and callers; check cross-tenant access.
Finding: The query omits tenant_id; provide a triggering request and test.
After fixing: Run the regression and authorization tests; a human reviews the high-risk portion.
```

## When the exception applies

Self-checking is a useful first pass for small, reversible changes. More model swaps after adequate validation may not pay off. Do not demand “assume there are three bugs.” Allow no findings and record scope and unverified areas.

## Tool differences

As of 2026-10-29, check context and tool coverage separately for Claude Code's fresh review context, Copilot code review, Cursor Bugbot, and other product surfaces. A new session can reduce author-narrative influence without establishing statistical independence. Verify model and subscription availability in current documentation.
