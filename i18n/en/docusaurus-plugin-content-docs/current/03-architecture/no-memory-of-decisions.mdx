> In one sentence: Automatic memory can recover past decisions, but it can also omit, misstate, or outlive them. Keep decisions and rationale in versioned ADRs. Before structural changes, I should check current records rather than rely on “I remember.”

## Symptom

Last month you rejected a separate event bus because its operating cost exceeded the needs of the current scale. Today I propose it again, or cite an old memory to defend a constraint that has been replaced. Either way, you repeat the decision process.

## Why this happens

A model's inference input and an agent product's persistent state are different things. Tools can store sessions, automatic memories, and project instructions and bring them into new context. Claude Code currently has auto memory; “every session has no cross-session memory” no longer describes such products accurately.

Saved does not mean retrieved for this task, correctly interpreted, or still valid. Code usually records an outcome, not rejected alternatives, conditions, or reconsideration triggers. Automatic memory is not a team-approved decision log either.

## Consequences

- I reopen rejected choices or restore an outdated design from stale memory.
- You mistake an automatic summary for an approved team decision.
- Similar descriptions from different projects become hard to attribute and scope.

## What to do instead

**Make ADRs the primary record and memories pointers to that record.**

1. Store versioned ADRs in a known directory: context, decision, rationale, rejected alternatives, consequences, status, and superseding records.
2. Keep short pointers in project instructions. Before structural work, I should cite the current ADR and check for replacements, explicitly reporting when none is found.
3. Keep necessary memory summaries with their sources, project scope, date, and invalidation conditions. Correct the primary record and inspect memory copies when errors appear.
4. Use the product's view, edit, disable, or delete controls. Do not retain secrets, temporary tokens, or unnecessary personal data in long-term memory.

## Example

**Before:**

```text
Me: I remember this project needs an event bus, so I'll add one.
You: That was another project. We rejected it here.
```

**After:**

```text
You: Check the current docs/adr/ decision before changing notifications.
Me: ADR-0012 chooses a status table plus polling; I found no superseding record.
    I'll follow it and propose reconsideration if its documented throughput trigger is reached.
```

## When the exception applies

Disposable prototypes do not need an ADR for every minor choice. For cross-module constraints, long-term maintenance, or contested decisions, retaining rationale is often cheaper than explaining it repeatedly. Automatic memory can locate evidence without proving the current decision by itself.

## Version notes

:::note Verified 2026-10-29
Memory persistence, scope, loading, and deletion vary by tool and version. This entry no longer claims all agents lack memory. Keep auditable decision evidence and check the version actually used for the task.
