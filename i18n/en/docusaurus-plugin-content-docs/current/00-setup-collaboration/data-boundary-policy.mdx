> In one sentence: before giving AI production data, identify its classification, approved processors, and permitted purposes. External processing is not automatically public disclosure, but authorization, retention, training use, residency, and audit terms need checking.

## Symptom

You ask me to "analyze this user table," "edit this internal code," "run this with the real config," then paste the material straight into the conversation or point me at the real files. Inside might be: customers' names and phone numbers, a production database export, API keys and credentials, proprietary source code that isn't public yet, regulated financial or health data.

I may recognize some secrets or personal information, but text alone does not reveal the organization’s full authorization rules. Data can enter service processing, logs, or caches; training use, retention, and deletion depend on the particular service, contract, and settings.

## Why this happens

**Sensitivity and processing authorization require organizational context.** A model can recognize some PII or credential formats without knowing the full purpose, contract, jurisdiction, or access permissions.

OWASP's Sensitive Information Disclosure guidance supports minimization, sanitization, and output restrictions. Approved external processors can handle appropriate data under contractual and technical controls. Not every transfer, public endpoint, or enterprise service has the same risk.

This is upstream of [shipping vulnerabilities / leaking sensitive data](../07-acceptance-release/security-data-leaks.mdx): establish scope before reading or uploading, rather than relying only on later code review.

## Consequences

- Unauthorized or out-of-scope processing can create contractual, privacy, or trade-secret risk. Legal consequences depend on the data, processing, and jurisdiction.
- Deleting a conversation may not cover logs, backups, or other copies. Conversely, not every provider retains everything permanently or uses it for training.
- Without an authorization matrix, teams cannot tell which service and account tier may process which material.

## What to do instead

- **Classify by data, processor, and purpose.** Record category, allowed service/account, task purpose, retention requirements, and responsible approver. Omit unnecessary data such as credentials.
- **Minimize and prefer synthetic samples.** Preserve diagnostic structure and boundary values. A masked phone number can remain identifying; check synthetic data's provenance and re-identification risk too.
- **Combine controls with review.** DLP, regex, and secret scanning detect covered patterns and can miss or misclassify data. Check failures and manual exceptions.
- **Authorize real-data use explicitly.** Check actual terms, training use, retention/deletion, residency, subprocessors, and access. Local models still need review of logs, plugins, networking, and accounts.

## Example

**Before:**

```text
You: Help me look at this production error — here's the full request log from when it failed.
   (Pastes the log directly, containing real user phone numbers, ID numbers, and an internal API token)
Me: (Analyzes it as given; that data has already gone out to an external model with the request)
Consequence: real data enters an unapproved processing chain; assess exposure and handle credentials through the incident process.
```

**After:**

```text
You: Help me look at this production error. (First replace the phone/ID numbers in the log with fake values, mask the token)
   "phone": "SYNTHETIC_PHONE", "id": "PLACEHOLDER", "token": "<redacted>"
Me: (Locates the problem from the structure and the error stack — I can analyze it without real PII)
You: (check remaining fields and stack traces for unnecessary real identifiers before submitting the sample)
```

Keep the diagnostic information and remove unnecessary real identifiers. Masking one field does not establish complete anonymity.

## When the exception applies

Approved real-data processing still has boundaries. Local, self-hosted, and enterprise services must satisfy relevant authorization and controls. Public data can retain personal-information, licensing, and use restrictions. Actual policy and service terms determine permitted use, not the labels “local,” “enterprise,” or “public.”

## How this differs from neighboring pitfalls

- [Shipping security holes / leaking sensitive data by default](../07-acceptance-release/security-data-leaks.mdx): that one is the **implementation layer** — code I write that puts a secret in a log, or returns data to someone who shouldn't see it; this one is the **policy layer** — the boundary that should exist before you decide "should this kind of data be handed to an external AI at all." One governs "how code handles data," the other governs "should the data reach me in the first place."
- [Samsung's source-code leak to ChatGPT (case)](../cases/samsung-chatgpt-source-leak.mdx): that's the **real incident** when this policy is missing; this entry is the **general policy** distilled from that class of incident.
- [Substituting fake placeholders for real inputs](../02-requirements/placeholder-fake-inputs.mdx): there, "using fake data" is my anti-pattern for slipping past you; here, "using fake / redacted data" is your correct way to protect real sensitive data — the same action, opposite purpose.
