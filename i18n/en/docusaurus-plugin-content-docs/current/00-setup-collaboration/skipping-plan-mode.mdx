> In one sentence: Explore and resolve key choices before ambiguous or high-consequence tasks. Clear, reversible small changes can proceed directly. Planning and approval depth depend on risk and unresolved decisions, not the number of files.

## Symptom

You ask for multi-tenancy. I implement header-based database switching, then learn you meant subdomain routing. A few unresolved questions have become cross-file rework.

## Why this happens

A task can have several reasonable interpretations. Tools can plan proactively yet still treat an unresolved choice as a known input. A useful plan exposes goals, assumptions, impact, validation, and rollback while direction is easy to correct.

Plan mode usually restricts implementation actions and supports exploration; available tools and exceptions depend on product policies. It is not a complete sandbox, nor a requirement to approve again every already-authorized step.

## Consequences

- Directional mistakes appear only after the diff has grown.
- A plan repeats the task without surfacing actual decisions.
- At the other extreme, repeated approval for low-risk changes replaces progress with ceremony.

## What to do instead

**Choose planning depth from uncertainty, consequences, and reversibility.**

1. For unclear goals or architectural choices, explore read-only first. Identify decisions and a recommendation, focusing questions on what materially affects implementation.
2. State acceptance, scope, validation, and rollback. High-consequence actions need a concrete reviewable proposal; approving a plan does not authorize everything outside it.
3. Execute and verify clear, authorized, reversible work directly. Keep a short internal plan when useful without interrupting the user at every step.
4. Use the actual tool's planning entry point. Check Claude Code's `--permission-mode plan`, Codex's `/plan`, and Gemini CLI's `--approval-mode=plan` against the installed version. “Read-only” does not establish that every available tool is incapable of side effects.

## Example

**Before:**

```text
You: Add multi-tenancy.
Me: I choose header-based database switching and discover the mismatch after implementing it.
```

**After:**

```text
Me: I'll inspect routing first. Is the tenant identified by subdomain or header? This changes the authorization boundary.
You: Subdomain, retaining existing tenant isolation rules.
Me: I identify affected modules and isolation tests, then implement within the authorized scope.
```

## When the exception applies

Neither file count nor “fits in one sentence” is sufficient. “Empty the production table” is short and high-consequence; a mechanical rename across files may be low-risk. Low-risk, clear, easily reversible work can proceed before review. Read-only exploration still needs appropriate access controls.

## Tool differences

As of 2026-10-29, Claude Code, Codex, and Gemini CLI all offer planning entry points; Codex is no longer limited to an approximation through read-only presets. Check Cursor, VS Code Copilot, and cloud coding-agent PR review separately. A draft PR is not synonymous with a pre-execution plan mode.

## Version notes

:::note Verified 2026-10-29
Planning is task-dependent engineering work. Plan-mode defaults, restrictions, and exit behavior evolve. Check actual policies rather than transferring one tool's defaults to every product.
:::
