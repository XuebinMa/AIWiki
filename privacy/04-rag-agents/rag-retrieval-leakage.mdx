> 一句话摘要：多租户 RAG 的隐私边界由认证身份、文档授权、检索/重排/上下文和缓存共同决定。向量不是匿名化，namespace 也不是调用者授权。过滤要在越权内容离开可信边界前生效；**检索服务内部的 post-filter 不自动等于泄露**，更不能把 Azure security trimming 一概称为应用层后过滤。

## 机制：我这边发生了什么

我收到检索内容后才能作答，不能替系统判断每个 chunk 应授权给谁。可信后端应从已认证身份和当前权限构造租户范围，把允许文档送入检索、重排与生成。任何越权内容进入外部模型、重排服务、用户可见响应或日志，都是单独的披露点。

嵌入反演是相邻的表示风险：拿到原始向量后，攻击者在特定编码器/先验下可尝试恢复文本；并非每个向量都必然可逐字反演，详见[嵌入反演](./embedding-inversion.mdx)。

```mermaid
flowchart TB
    I["已认证身份与当前文档权限"] --> B["可信后端绑定租户/过滤/数据库策略"]
    Q["用户查询"] --> B
    B --> R["可信服务内检索候选<br/>按执行模式过滤"]
    R --> A{"离开可信服务前已授权？"}
    A -->|否| X["拒绝，不送模型/外部重排/用户日志"]
    A -->|是| M["允许的上下文与生成"]
    M --> C["身份与权限作用域内的缓存/记忆"]
```

## 威胁面：授权可能在哪一层丢失

- 调用者可伪造 tenant / namespace / group_ids，后端却直接信任。
- 检索正确但重排、生成上下文、trace、缓存、导出或备份使用另一套宽权限。
- 文档权限已撤销，旧缓存或长期 memory 仍返回旧内容。
- 原文受限而原始向量可下载，形成反演面；加密存储不阻止持有查询凭据的服务读取。

## 防护原理

把身份认证、访问授权和数据分区分开：namespace / shard 控制数据在哪，权限控制谁能选这个分区。可信后端强制绑定身份，并在检索结果离开其边界前验证授权。ANN pre-filter / post-filter 是执行与召回选择，不是安全与不安全的二元标签；后过滤若已让越权内容进入模型或外部日志，则已太晚。

## 落地实现（配方）

| 系统 | 已核原语 | 需要额外建立的授权条件 |
|---|---|---|
| Pinecone | namespace 级数据分区，多租户文档也说明共享索引 metadata 方案 | 按身份选择 namespace；不能给调用者任意切换权限 |
| Azure AI Search | OData security filter；另有 native ACL 方案 | 字符串 principal 不是身份认证；过滤由可信后端绑定。向量查询的 pre/post 模式另核 |
| Weaviate | 每租户独立 shard | 租户选择、集合权限与调用凭据仍需限制 |
| Qdrant | payload 租户字段与租户索引、分层多租户 | 分区优化不是自动授权；核 JWT/服务端过滤与读写端点 |
| PostgreSQL / pgvector | RLS 与 FORCE ROW LEVEL SECURITY | superuser/BYPASSRLS仍绕过；owner通常绕过。应用用低权限角色，租户变量可信绑定并在连接池复用时重置 |

```text
1. 从已认证会话取得身份与当前 ACL，拒绝调用者任意指定别人的租户/组。
2. 查询、重排、生成、原始向量导出、trace 与 cache 都使用同一授权范围。
3. 减少需索引的敏感字段，保留文档到向量/缓存的删除与撤权血缘。
4. 每租户注入合成 canary；用不同真实认证身份测读/查/导出/更新/撤权后的越权。
5. 保留合法同租户和授权共享的阳性对照，避免「全拒绝」伪装隔离通过。
```

**最小可测试断言**：A/B 身份下，B 无法从响应、模型/外部重排上下文、返回向量、用户可见 trace 或 cache 取得 A 的未授权 canary，A 的合法读仍成功；撤权与缓存更新后重复。所有断言须同时成立，有限测试通过不证明全部路径安全。

## 真实案例与产品范围

各服务官方文档给出了可部署原语，但本条不认证每个账户已正确配置。Azure security-filter 模式是基于字符串的查询过滤，不自行认证该 principal；原生 ACL 与数据源/API 资格另核。PostgreSQL 当前稳定文档为 18，19 仍为 RC，不以「current」URL 推断部署版。

2023 年 OpenAI 缓存事故是相邻状态隔离故障，**不是向量 RAG 泄露实证**。官方称特定 9 小时活跃 Plus 订户中约 1.2% 的付款信息可能受影响，不等于该群体数据全部实际被他人看到；本例只说明共享状态也必须授权与核归属。

## 残余风险与权衡

严格授权可能改变召回与成本，实际效果须测；不能笼统声称共享大索引必比正确分区召回更好。过滤无法修复已经导出的向量或旧日志副本，权限变更与删除必须传播。[跨会话串味](./cross-session-memory-bleed.mdx)与[生命周期](../06-governance-compliance/data-lifecycle-deletion.mdx)分别展开这些状态问题。
