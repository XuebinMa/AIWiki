> 一句话摘要：“整个仓库都放进窗口了”不代表我能可靠用好每一处。长上下文的影响取决于模型、任务、位置与信息组织；保留需要的全局证据，再验证关键约束是否真正被用到。

## 现象

你给我二十个文件和几千行日志。我漏掉了其中“金额必须存整数分”的约束，却流畅地交出了浮点实现。材料确实在输入里，结果仍没有满足它。

## 为什么会这样

研究为这种风险提供了证据，但没有证明所有模型都遵循同一条退化曲线。*Lost in the Middle* 在所测模型的多文档问答和键值检索中，观察到信息位置会影响表现，中间位置常更差。2025 年的 *Context Length Alone Hurts...* 在五个模型的若干任务中，即便检索完美、无关 token 被屏蔽，仍测到长度增加带来的退化。

这些结果支持“标称容量不等于可靠利用”，不能仅用“token 更多、注意力分母更大”解释所有结果，也不能推断每个新模型必然同样退化。缺少材料、检索错误、压缩丢失与模型未正确利用材料，应分别排查。

    A[需要的证据] --> B[检索 / 组织 / 必要时摘要]

## 后果

- 我遗漏已提供的约束，你却因为“全给了”放松验收。
- 无关日志挤占空间与成本，补得更多未必改善结果。
- 为了缩短而删掉调用方或契约，又会造成另一种信息缺失。

## 最佳实践

**精选与任务有关的证据，并验证覆盖；不要把“短”本身当成目标。**

- 先定位代码、失败输出和约束，保留能追溯到原文件的引用；跨文件重构仍要读调用方与共享契约。
- 关键要求用清晰标题标注，需要时在当前请求重申；不同位置、检索与摘要策略的效果用代表任务比较。
- 用关键约束清单或可执行检查验证结果，而不是靠我声称“都看过了”。
- 相关长任务用[压缩后的恢复检查](./compact-timing.mdx)维持状态；切换无关任务时考虑[新会话](./kitchen-sink-session.mdx)。
- 把常驻规则保持简洁，见[CLAUDE.md 过载](./claude-md-overload.mdx)，但不要遗漏完成任务必需的证据。

## 示例

**改之前：**

```text
你：整个目录和日志都在上面，按里面的要求改。
我：交付了浮点金额实现，漏掉整数分约束。
```

**改之后：**

```text
你：先读 money 模型、金额约束和相关调用方，列出单位转换位置。
    金额用整数分；用负数、边界和跨接口用例检查这一约束。
我：按引用确认约束，完成实现并提供检查结果。
```

## 什么时候例外

全局一致性检查、长文档对照或跨模块分析可能确实需要较多材料。先索引、再按需要取完整片段；检索不到就扩大范围。不要为了省 token 把必要上下文裁掉，也不要假定重复置顶就能保证遵守。
