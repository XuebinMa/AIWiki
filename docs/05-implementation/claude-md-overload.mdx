> 一句话摘要：你把所有想到的规范都写进 `CLAUDE.md`，希望我面面俱到。规则过多或互相冲突时，我可能漏掉关键要求；要检查实际加载与任务结果。

## 现象

`CLAUDE.md` 是我每次都会读的项目说明书。我常看到它被越写越长：编码风格、目录约定、命名规则、提交格式、几十条「务必」「禁止」……初衷是好的，但当它长到几百行时，你会发现我开始忽略其中一部分——而且未必是你觉得最不重要的那部分。

## 为什么会这样

常驻指令占用上下文，也可能相互冲突、包含过期约定或与代码现状不一致。规则越多，维护和验证越困难；但没有一个对所有前沿模型都成立的“可靠遵循 150–200 条指令”定额。

不要只数行数。更该检查：哪些信息我能从仓库直接发现，哪些只对局部路径有效，哪些是真正的团队约定，以及哪些红线应该由权限、hook 或 CI 执行。

## 后果

- 关键约束被漏掉，而你以为已经「写在规范里了」。
- 文件越长，每次会话的固定开销越大，留给实际任务的窗口越小。
- 你很难判断到底哪条规则在起作用、哪条形同虚设。

## 最佳实践

**保留有用途的短指令，并验证实际加载与效果。**

1. 留下真实构建/测试入口、无法从代码推得的决定和容易踩错的约定。
2. 重复错误先诊断：是没加载、互相冲突、过期，还是需要执行控制；不要每次都追加一条“务必”。
3. 删除过期、冗余或已迁移到执行控制的规则；“从没违反过”不能单独证明一条安全约定多余。
4. 局部规则按路径加载，多步流程按需放入 skill；核查引用与自动记忆实际增加了哪些内容。
5. 用代表任务检查关键约束是否被用到，比较删减前后结果，别把文件短当作唯一指标。

## 示例

**改之前（节选，共 200+ 行）：**

```markdown
- 变量命名用 camelCase
- 不要用 var
- 注释要写完整句子
- 函数不超过 50 行
- 优先用 const
- 每个文件顶部要有版权头
- ……（还有 190 行）
```

**改之后（10 行，每条都对应一次真实教训）：**

```markdown
# 构建与测试
- 改完代码跑 `npm test`，全绿再交。

# 这个项目踩过的坑
- 数据库迁移必须可回滚（上次漏了导致线上事故）。
- 时间一律用 UTC 存储（混用时区出过 bug）。
```

## 工具差异

截至 2026-10-29：Gemini CLI 的层级上下文、Codex 的 `AGENTS.md`、Cursor 的条件规则、Copilot 不同产品形态的自定义指令，都有各自发现与加载方式。核查累计加载、作用域、长度限制和截断提示；不要只看你编辑的那一个文件。具体上限与默认值以当前官方文档为准。
