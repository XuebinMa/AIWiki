> 一句话摘要：跨十几个文件的大重构做到一半，我就记不清改到哪了——哪些文件已改、哪些没改、那个改名是否全仓同步了。于是漏改一处编译挂掉、把已改的又改一遍、前后用了两种不一致的写法。别让我用记忆当待办清单。

## 现象

你让我把一个用得到处都是的函数 `getUser()` 改名成 `fetchUser()`，顺带把它的返回类型从裸对象换成 `Result<User>`。这是个典型的跨文件重构：调用点散在十几个文件里，每个调用点都要跟着改。

我开始一个个改。改到第七、第八个文件时，你会看到这些症状：

- 我漏掉了 `legacy/` 目录下还有两处调用，编译直接挂在那里。
- 我把 `services/auth.ts` 又打开改了一遍——其实我十分钟前已经改过它了。
- 前五个文件我用了 `Result<User>`，后五个不知不觉退回成了 `User | null`——同一次重构里出现了两种返回约定。

## 为什么会这样

跨文件重构需要一份可检查的状态：受影响调用点、已改内容、待验证行为和兼容边界。我如果只凭对话印象报告进度，就可能漏改或重复编辑。

代理可以使用清单、任务工具和持久文件，不能笼统说我没有任何稳定记忆。当前 Claude Code 压缩后会重新载入部分规则、计划、记忆及文件，**也不能说压缩一定抹掉所有早期决定**；具体保留内容与版本和载入方式有关。

外置记录仍要与真实代码对账。搜索只覆盖匹配形式，可能漏掉别名、动态访问、字符串协议、生成代码及仓外调用；零命中不等于行为迁移已完成。

## 后果

- **漏改**：有调用点没跟着改，编译挂掉，或更糟——编译过了但行为变了，藏到运行时才炸。
- **重改**：我把已经改好的文件又改一遍，可能把对的改回错的，白白浪费你的 review。
- **前后不一致**：同一次重构里出现两种写法（`Result<User>` 和 `User | null`），等于在重构里又埋了一笔新的技术债。
- **越查越乱**：你让我「检查一下哪里还没改」，我凭记忆回答，而记忆本身就是出错的源头——你拿到的是一份不可信的进度报告。

## 最佳实践

1. **先发现，再维护清单。** 搜索定义、引用、字符串契约与已知仓外使用方；把未知范围写出来。清单在磁盘或任务工具里也要随实际 diff 更新。
2. **按完整逻辑小步推进。** 类型改动可能要求多个文件一起改变，不能强求每个文件单独编译通过。每个连贯步骤验证后，按既有授权和项目规则提交。
3. **搜索与行为验证互补。** 搜索旧符号并分类解释剩余命中，另检查别名、动态调用、生成产物与对外兼容；最终运行与变更有关的检查。
4. **恢复工作时核对现状。** 先看清单、diff 和真实文件，再继续，避免把已完成项当未完成。

## 示例

**改之前：** 我连续改十几个调用点，仅凭印象说「都改完了」，遗漏 legacy/ 和动态入口。

**改之后：**

```text
我：先搜索 getUser 的定义、调用和导出，并记录已知动态 / 仓外入口。
    把 getUser → fetchUser 与 Result<User> 作为连贯的逻辑步骤迁移；
    必要时一组文件一起改，再跑对应类型和行为检查。
    最后分类核对旧名残留、兼容入口与任务清单，给出实际检查输出。
```

搜索归零只是证据之一；仍需确认新返回类型的成功、失败与兼容行为。
