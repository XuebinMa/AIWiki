> 一句话摘要：我可能反复请求模型或工具，却没有取得新进展，累积费用并重复副作用；调用、时间、预算和权限需要执行器分别计量与约束，提示词不是硬上限。

## 现象

无人值守运行时，我可能把一次临时失败当成无限重试理由，或在两个互相破坏的修法之间反复切换。若每次都重新请求模型、调用工具，成本会累积；若工具有副作用，重复请求还可能反复写入外部系统。

公开 issue #15909 的报告者在 2025-12-31 描述了一个后台子代理重复安装命令 300 多次、约 4.6 小时及约 2700 万 token 的情况。**这些是报告者给出的数字，本文未独立复现或核对账单**；它证明有这样的公开报告，不给出当前版本的发生率。

## 为什么会这样

我可能重复同一失败动作，而循环控制器没有判断重复、进展和剩余预算。模型、代理编排和工具实现都会影响这种行为；成本和退出控制不能只交给一句「别重试太多」。

MAST 分析受测多代理框架的设计、协作与验证失败；其中过早终止不等于非终止循环的证明。Agents of Chaos 是特定实验室环境的探索性红队案例，说明资源与副作用失控可以发生，并不提供所有部署的发生率。公开 issue 则是用户报告，不能因位于厂商仓库就当成厂商复现结论。

我应让执行器维护调用次数、超时、重试分类、已完成状态和副作用标识；达到规则就停止或交接，而不是期待我可靠地凭感觉判断成本。

## 后果

- **账单与配额被烧穿。** token 按量计费，循环里每一轮都在花钱；订阅制下还会撞上滚动窗口的用量上限，把你接下来几个小时锁在工具外。一个本该几分钟的小任务，能拖成几十分钟的空转和一笔莫名其妙的开销。
- **对外部系统的反复副作用。** 如果循环里有会真正写入的工具，最坏情况不是浪费，而是破坏：对同一接口连发请求触发对方限流甚至封禁，反复创建 / 删除资源把外部状态搅乱。red-team 研究在放养式部署里就观测到过「不受控的资源消耗」「拒绝服务式」的代理行为（见 *Agents of Chaos*）。
- **上下文被失败尝试填满。** 每一轮没进展的尝试都留在窗口里继续稀释注意力，让我后续更难跳出循环——和[厨房水槽式会话](./kitchen-sink-session.mdx)是同一种信噪比塌缩，只是这次是我自己往里灌噪声。
- **你被「快好了」的假象拖住。** 每一轮我都像在推进，你就再等一会儿——等到发现不对，时间和钱都已经花掉了。

## 最佳实践

- **在执行器里计数与限制。** Claude print 模式可设 --max-turns；另在控制器设置工具调用、并发子任务、每次请求输出、总时间及重试上限，并验证实际终止行为。
- **费用上限留余量。** 客户端估算可能滞后，一次调用和并行任务也可能超预算。调用前预留预计开销、限制单次消耗，并在接近阈值时取消待处理工作；不要把本地估算或告警说成精确账单硬顶。
- **按失败类型重试。** 临时故障使用有界退避；鉴权、缺配置或确定无效输入先修前提。同一动作无新证据不再原样重发。
- **副作用独立控制。** 写请求使用工具侧幂等、去重与限流，按已授权风险边界执行；只有越界或高代价操作需要额外批准。模型暂停不等于远端请求被撤销。
- **保留可恢复进度。** 外置已完成项、失败原因和下一步；停止时报告已知状态与未确认的副作用。

## 示例

**改之前：**

```text
你：把这个目录下所有图片调用 API 压缩一遍，自动批准，我去开会
（开了 --dangerously-skip-permissions，没设任何上限）

我：（其中一张图触发了一个会重试的 API 错误）
    重试…失败。再试…失败。再试…失败。
    （把同一张坏图对同一接口连发了 200 次，对方开始限流，
     连带把后面正常的图也卡住，token 和配额一路烧）

你：（一小时后回来）……账单怎么这么高？这才压了三张图？
```

**改之后：**

```text
你：把这个目录下的图片调用 API 压缩。约定：
    - 单张失败最多重试 2 次，再不行就跳过并记下来，别死磕
    - 整个任务最多 30 个工具调用，到顶停下来报告进度
    - 调用 API 的命令保留确认，不进自动批准

我：第 1 张：失败 2 次（疑似图本身损坏），已跳过并记录。
    第 2–9 张：成功。
    达到约定的失败处理规则，未触发上限。要看跳过清单吗？

你：（用量正常，没有一张图被重发上百次，外部接口也没被打爆）
```

差别不在我「这次更克制」，在于你把「最多试几次、什么时候停、哪些动作要确认」这些我判断不可靠的事，提前用规则和上限定死了。

## 工具差异

2026-10-29 的 Claude CLI 文档列出 print 模式的 --max-turns 与估计费用限制，后者明确可超出阈值；流式新输入与子代理还需按其计量范围处理。Gemini 配置列的是 model.maxSessionTurns，默认 -1；不能只靠默认值，也要测试所用版本的执行行为。

Codex 的审批与沙箱限制允许做什么，不自动成为 token、总调用或费用预算。旧 suggest / auto-edit / full-auto 档位表不再作为当前配置说明。无论客户端如何，必须分别验证允许的动作、执行期限和消耗上限。
