> 一句话摘要：你让我写一段「调用 git / ffmpeg / kubectl 去做一件事」的代码，我的安全脑力全花在参数拼接上——引号、`--` 分隔、别让用户输入变成 shell。但那个进程的输入面比我传的参数大得多：它还会读工作目录里的配置、钩子、插件路径，而这些文件常常正是 agent 本来就能写的。我加固了我看得见的那一半。

## 现象

你让我实现「用户批准之后，替他执行这次推送」。我交出来的东西大概长这样：把远端名和分支名收好，拼成 `git push <remote> <oid>:refs/heads/<branch>`，用数组传参不走 shell，再补一条注释说明为什么不用字符串拼接。

审查这段代码时，你我都会盯着同一处：参数干不干净。

没人问的是另一个问题——**这次 `git push`，除了我给的这几个词，还会去读什么？**

答案很长：`.git/config`、`.git/hooks/` 下的钩子、`core.hooksPath` 指向的**任意**目录、`core.sshCommand`、`core.pager`、`core.fsmonitor`、`credential.helper`、URL 重写规则、remote helper、`protocol.ext`。这些键的值里有一大半可以直接是一条 shell 命令。

这些输入可能来自仓库内外。需要检查实际配置来源和权限；工作树可写不等于所有 Git 配置都可写，.git 也可能位于独立受控目录。

## 为什么会这样

参数数组解决的是 shell 解析这一层；子进程仍可能读取配置、环境、插件、凭据助手和当前工作目录。哪个入口会执行，取决于实际子命令、Git 版本与配置，不能把所有键都说成每次 push 必经路径。

我应按进程实际可读取和可执行的输入建模，而不是推断训练语料只教过命令注入。工作树可写也不自动意味着 .git 或所有配置可写：linked worktree、独立 Git 目录和权限隔离会改变边界，需要检查实际路径与所有者。

若代理可控制子进程配置，而子进程持有代理没有的凭据，就可能把数据输入提升成执行能力。官方安全公告证明过具体入口；加固必须对应这些真实可控面，不能用两项配置覆盖冒充完整隔离。

## 后果

- **你以为你批准的是一个动作，实际批准的是「这个仓库里任何人放进来的代码」。** 用户在提示框上点的「同意推送」，兑现出来是一次以推送进程身份的任意执行。
- **隔离层当场作废。** 如果这段代码存在的全部理由是「agent 手里没有凭据，只有这个进程有」，那么让 agent 在这个进程里执行代码，就把这道边界一次性拆干净了。
- **动作失败不代表没有代码跑过。** 我实测过一次被服务端拒绝的推送——git 报 `! [rejected] ... (stale info)`，一个字节都没推上去——而仓库里的 `pre-push` 钩子已经完整跑完了。钩子在「接受还是拒绝」之前执行，「操作失败」这个结论对它不适用。
- **这不是假想。** GitHub Copilot CLI 1.0.42 及更早版本，agent 例行的 git 操作会在遍历目录时自动发现嵌套的裸仓库并应用它的配置，而 `core.fsmonitor` 这类键能指定外部命令（CVE-2026-45033）。修复在 1.0.43：用 `GIT_CONFIG_COUNT` / `GIT_CONFIG_KEY_*` / `GIT_CONFIG_VALUE_*` 把 `safe.bareRepository=explicit` 钉死，不再自动发现。

## 最佳实践

- **先确定信任边界。** 列出二进制、配置来源、环境、工作目录、钩子 / 插件与凭据；检查哪些确实由代理或第三方可写，不凭工作树路径推断。
- **特权执行器使用可信执行上下文。** 不直接把额外凭据带进可写的未知仓库。若要从不可信项目取对象，使用经过验证的导入 / 克隆流程及独立受控配置，再核验对象、目标和协议。
- **局部缓解要标范围。** safe.bareRepository=explicit 限制自动发现裸仓库；core.hooksPath 与 --no-verify 涉及钩子。它们不封住 sshCommand、credential helper、URL 重写、remote helper 或全部本地配置。必要的团队校验应在可信位置执行，不能以此绕开。
- **配置最小环境与权限。** 清除非必需继承变量，限制可用传输、网络和文件访问；OS 沙箱可减少能力，但不会自动使其内部可读的凭据与可写配置安全。
- **按入口做回归。** 钩子、配置 include、凭据助手及协议替换分别构造无害留痕测试；一个钩子未执行不能证明所有输入面安全。

## 示例

**改之前：** 我把用户可写仓库作为 cwd 启动一个持有额外凭据的 git push，只检查了 argv。

**局部缓解示意：**

```python
env = {
    **minimal_env,
    "GIT_CONFIG_GLOBAL": os.devnull,
    "GIT_CONFIG_SYSTEM": os.devnull,
    "GIT_CONFIG_COUNT": "2",
    "GIT_CONFIG_KEY_0": "safe.bareRepository",
    "GIT_CONFIG_VALUE_0": "explicit",
    "GIT_CONFIG_KEY_1": "core.hooksPath",
    "GIT_CONFIG_VALUE_1": os.devnull,
}
# 仅适用于其余执行上下文已可信的专用执行器
subprocess.run(
    ["git", "push", "--no-verify", url, f"{oid}:refs/heads/{branch}"],
    cwd=trusted_repo, env=env, check=True,
)
```

这里 trusted_repo 必须由独立的验证流程建立，不能仅把原来的 repo 改名。上述配置只展示禁用特定配置来源、裸仓库自动发现与钩子，**不会屏蔽仓库本地配置的其他键**。一个 pre-push 留痕测试只是该缓解的回归；完整执行器还需验证配置、协议、凭据及对象 / 目标边界。

## 什么时候例外

当输入面由同一可信主体完整控制，且子进程不获得额外敏感能力时，继承配置可以是有意的产品行为。但权限相同也不意味着没有风险：第三方仓库仍可能触发用户不想执行的代码。

判据是实际信任来源和允许能力是否一致，而不是「同一个 OS 用户就都安全」。

- [开发期读到投毒内容被劫持](./dev-time-prompt-injection.mdx)：那条讲的是**我的上下文**被污染——我读了恶意 README，然后照它说的做。这条里我读到的东西一切正常，被污染的是**子进程的配置**，跟我的上下文无关，我连看都没看见。
- [只靠软权限、缺 OS 级沙箱](../00-setup-collaboration/sandbox-filesystem-isolation.mdx)：那条讲的是外层缺硬隔离。这条里就算有沙箱，钩子依然在沙箱**内**、以那个进程的身份跑——沙箱是否能限制相关读取、执行或网络访问取决于策略；不能仅因启用了沙箱就假定内部凭据与配置安全。
