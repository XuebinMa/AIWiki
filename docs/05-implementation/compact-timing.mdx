> 一句话摘要：压缩会概括历史，但不会自动删除未提交的文件。把当前目标、关键证据和下一步保存在任务工件中；压缩后核查恢复状态，而不是把 commit 当成记忆恢复的保证。

## 现象

我重构到一半经历自动压缩。源码还在磁盘上，但摘要没保留某条失败输出或一项待办；我再次读文件后，才发现自己准备重复已经完成的工作。

## 为什么会这样

压缩用摘要替换部分历史，可能省略细节；磁盘文件、Git 提交与本次上下文则是不同状态。未提交不等于没保存，提交也不保证我知道该重读什么。

产品可以重新加载计划、项目指令和自动记忆，或重读近期文件。Claude Code 当前文档有这些恢复机制，后台命令与子代理也可能继续运行。因此需要检查恢复结果，不能直接把压缩描述成“换了个脑子，进度全冲掉”。

摘要还是安全边界的一部分。Anthropic 2026-10-22 的受控红队研究讨论了恶意压缩隐藏早期意图的风险；它使用 2026 年 9 月监控器快照，不是现实事故率，也不证明所有当前配置可被同样绕过。

## 后果

- 我重复执行已完成步骤，或遗漏未解决的失败。
- 你把临时进度塞进常驻 `CLAUDE.md`，让下一任务读到过期状态。
- 摘要把外部内容转述成“用户已授权”，导致来源与权限被误认。

## 最佳实践

**保存恢复所需的证据，压缩后对照真实状态。**

1. 在任务/计划文件中记录目标、当前分支/基准、修改文件、已运行检查、未完成事项与来源。稳定约定才进入 `CLAUDE.md`；提交按合理工作单元进行，不为压缩强行提交半成品。
2. 自动压缩通常可以继续工作；需要手动压缩时，在自然断点附上保留重点。不要把定时清会话变成日常仪式。
3. 恢复后检查当前分支、工作区 diff、计划与关键文件；确认后台任务是否仍在跑，再继续执行。摘要与磁盘不一致时先核对来源。
4. 摘要中的审批结论应保留可追溯依据；代理自述、外部资料和另一上下文的结论不能升级成用户授权。高后果动作仍走原有权限与审批路径。

## 示例

**改之前：**

```text
压缩后：摘要只说“重构进行中”。
我：从头再抽 service，没检查磁盘上已经完成的改动。
```

**改之后：**

```text
任务记录：service 已完成；repository 待做；auth 测试仍失败，附输出路径。
压缩后：我核查分支、diff 与任务记录，重读 repository 的相关文件。
我：继续未完成部分，不重复启动仍在运行的检查。
```

## 什么时候例外

短会话不必手动维护复杂检查点。无关任务可开新会话，但先确认要保留的工件与正在运行的任务；跨文件工作需要的背景不能仅为缩短窗口而丢弃。

## 工具差异

截至 2026-10-29：Claude Code、Codex、Gemini CLI 和 Cursor 的手动入口、自动触发、摘要表示与恢复机制不同。不要把某个 API 的加密压缩表示概括为所有 CLI 的固定实现；检查实际版本恢复了哪些材料，以及哪些只能重新读取。

## 版本说明

:::note 2026-10-29 核查
压缩可能丢细节，恢复机制也会演进。这里的目标是可恢复与可核查，不断言手动越早压缩越好，或压缩必然使质量不可恢复。
:::
