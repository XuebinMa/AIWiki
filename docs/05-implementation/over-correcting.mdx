> 一句话摘要：反复纠正若没有增加可靠证据，我可能继续沿用失败假设；应保留已知事实、排除的方案与下一项验证，并把精简上下文和恢复代码分开处理。

## 现象

我给了一个不对的实现。你说「不对，应该用 B 方案」。我改了，但还是带着原来的毛病。你再纠正，我又改，结果偏得更远。来回三四轮，你开始怀疑我是不是根本不理解需求。

## 为什么会这样

我可能把之前失败的假设继续作为前提，即使你已指出错误；但纠正并非只会越纠越差。新日志、最小反例和明确的规格也能让同一会话收敛。问题是后续尝试有没有增加可靠信息，而不是轮数本身。

旧消息可能被压缩、裁剪或检索回来，不能说每轮的全部错误始终原样占在窗口里。跨会话规则和持久记忆也因产品而异；纠正并不自动训练模型，但可以更新显式记录，供后续读取。

我应提炼已排除的方案、当前证据和待验证假设；必要时换一份精简上下文，而不是机械地删除所有历史或恢复所有文件。

## 后果

- 表面在「修」，实际在错误地基上反复打补丁。
- 上下文被失败尝试填满，进一步拖累后续质量（见[厨房水槽式会话](./kitchen-sink-session.mdx)）。
- 你花在纠正上的时间，超过了重新开始本该花的时间。

## 最佳实践

- **先问这一轮学到了什么。** 我应列出已否定假设与新证据；没有新信息的重复尝试先停下来重新定位。
- **精简上下文时保留证据。** 把目标、约束、失败原因与最小复现写成简短摘要，再决定继续原会话、开新会话或清理上下文。
- **代码回退单独处理。** 使用 /rewind 或双按 Esc 打开菜单后，核对所选的代码 / 对话恢复范围；先保护用户及并行工作。外部 API、数据库或只由 shell 修改的未追踪文件不能假定一起撤销。
- **把经验存成显式规则。** 只保存已验证、仍适用的结论；不要把一次猜测写进长期记忆。

## 示例

**改之前：** 我反复把递归换个写法，仍未解决栈溢出。

**改之后：**

```text
我：已知要求是深层遍历；递归版本在受测深度失败。
    下一次只验证迭代实现，并保留失败用例。
    若需清理对话，先保存这些事实；若需撤回代码，先检查当前 diff，
    在恢复菜单中选择准确范围，保护其它改动。
```

这会给下一轮提供可检查的起点；是否成功仍以实际用例和资源限制验证。

## 版本说明

:::note 适用版本
2026-10-29 核验当前最佳实践、memory 与 checkpointing。两次纠正可作复盘提醒，不是硬阈值。/rewind 会打开可选恢复 / 摘要操作；对话与代码恢复应分开判断，当前追踪文件上的后续外部改动也可能被恢复覆盖，链接路径另有限制。
:::
