> 一句话摘要：我可以迅速堆出功能，也可能把维护成本推迟到后续修改。没有普遍的「三个月期限」；应根据真实变更阻力决定何时偿还技术债。

## 现象

重复逻辑和隐式依赖让首版很快完成。下一次改需求时，同一个规则散落多处，修一处又坏一处；速度开始下降。

## 为什么会这样

技术债是解释未来变更额外成本的隐喻。Fowler 特别指出，利息通常在你修改相应区域时支付；稳定且不再变化的粗糙代码可能值得暂时保留。其成本讨论是实践判断，不是「所有项目三个月撞墙」的测量结论。

我可能局部修补而没有检查结构和历史决策。自动记忆也不等于经过维护的架构记录；重要取舍仍应放进可审查的 ADR 或项目文档。

## 后果

常改模块的交付变慢，重复修复增加回归机会，团队却可能为几乎不变的区域过早重构。

## 最佳实践

1. 记录已知债务、触发条件和影响的变更，不把每个不够漂亮的地方都登记成紧急债务。
2. 优先治理反复修改、反复出错的热点；用真实耗时和缺陷观察判断回报，避免无依据的精确收益估计。
3. 在功能改动附近做小步重构并验证旧契约。只有需求支持时才抽象，不为假想未来统一所有代码。
4. 用 ADR 记录关键边界、取舍和何时重看；参见《[决策没有记忆](../03-architecture/no-memory-of-decisions.mdx)》。

## 示例

```text
改之前：五处复制计费规则；每次改价都逐处修补。
改之后：记录重复带来的真实修改成本，集中反复变更的规则并补回归；长期不动的独立脚本暂不重构。
```
