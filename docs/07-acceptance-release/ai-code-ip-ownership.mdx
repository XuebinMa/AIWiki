> 一句话摘要：我生成了一段代码，并不等于它的版权、合同权利、第三方许可和责任都已厘清。把这些问题分开核对，才能判断它能否成为你的可交付资产。

## 现象

你把我的输出直接登记为公司原创代码，却没记录人的创作贡献、供应商条款或第三方来源。直到客户要求权利保证，才发现「能运行」没有回答「有什么权利」。

## 为什么会这样

**版权保护、合同归属、第三方许可、责任分配是不同问题。** 美国版权局 2025 年报告强调人的作者身份，并按具体贡献判断保护范围；现有一般技术下，仅有提示词通常不足，人类创作的输入、选择编排或修改则可能获得保护。这是美国版权可保护性的分析，不是全球归属或赔偿责任的统一答案。

我对来源的自述不是可靠的出处证明。代码相似也不自动等于侵权：还要核对受保护表达、授权、使用方式和适用法。合同约定「输出归用户」也不能凭空消除第三方权利。

## 后果

- 你可能承诺了自己无法证明的独占权利或来源保证。
- 第三方许可义务可能影响交付方式；版权与专利问题还需分别评估。
- 发生争议时，责任要依合同和适用法律判断，不能预设全部由用户或供应商承担。

## 最佳实践

1. 记录工具、条款版本、人的实质创作和审查过程；不要把生成日志当成版权证书。
2. 对关键模块核对来源和依赖许可，保留要求的声明、通知及源码提供安排。GPL / AGPL 的条件取决于受覆盖作品、组合和传播方式；不是引用一个依赖就自动要求整个产品开源。
3. 把相似性扫描用于发现线索。没有命中不代表无第三方权利；改写也不自动消除许可义务。
4. 在对外给出重大权利保证前，由负责合同或法务的人审查具体代码、合同和法域。

## 示例

```text
改之前：AI 写的，所以公司有完整版权，可以给客户独占保证。
改之后：分别记录人的创作、供应商合同和第三方许可；未核清部分不作独占保证。
```

## 版本说明

:::note 适用范围
本条以美国版权局报告与 GPL / AGPL 许可文本核对概念，不对具体代码作法律结论，也不转述未经一手裁判核实的诉讼现状。法域、司法解释、合同或许可变化时应重新审查。
:::
