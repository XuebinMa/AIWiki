> 一句话摘要：我把限制写进文档，只证明我描述过它；要判断边界是否有效，还得检查实现、部署和运行证据。

## 现象

交付说明写着「仅本机访问」「不留存」「只读」「异常时拒绝」。你据此放心，但实际监听地址、日志保留和数据库凭据没有逐项核对。

## 为什么会这样

描述意图与证明控制有效是两种工作。NIST SP 800-53A 的评估方法包括检查资料、访谈和测试，并允许按风险裁剪；不是所有控制都能靠一个自动化测试证明，也不是没有可执行测试就等于完全没检查。

我可能把局部测试概括成整体保证，或把「代码中有开关」误写成「部署中已启用」。文档越完整，读者越容易忽略证据范围。

## 后果

未启用的边界被当成已经生效；部分覆盖被宣传成全面保护；事故后找不到当时的配置、检查人和检查条件。

## 最佳实践

1. 给每项重要声明写清控制位置、负责方、适用配置和核验日期。
2. 选合适证据：检查实际配置与代码、核对运维流程、运行正向和反向测试；对无法测试的部分说明原因。
3. 区分「设计如此」「本环境观察到」「在所列测试下通过」，避免把三者写成同一个保证。
4. 高风险边界请独立审查，但不要把独立性或审查时长当成有效性的自动证明。

## 示例

```text
改之前：“只读访问已保证。”（依据：文档中有 read_only 参数）
改之后：测试账户实际无写权限；写入请求在指定环境被拒绝；管理员凭据路径不在这次核验范围内。
```

## 版本说明

:::note 证据范围
NIST 是控制评估方法，不是本项目已通过认证的证明。限制、部署或负责流程变更时重新验证；没有发现绕过，只能说明已检查范围内未发现。
:::
