> 一句话摘要：我可能遗漏鉴权、输入处理或秘密管理。功能跑通不能证明安全；显式安全要求、自动检查与人工核对需要一起工作。

## 现象

硬编码密钥进了源码，查询拼接外部输入，错误响应或日志包含 token。主路径仍能通过，但权限失败和敏感数据路径没有被检查。

GitGuardian 2026 报告在公开 GitHub 的观察中，给 Claude Code 辅助提交测得 3.2% 的秘密检出率，对照基线为 1.5%。这是特定识别方法下的关联，不能推广为所有 AI 提交，也不能证明工具导致泄露。

## 为什么会这样

我可能漏掉安全约束，现有代码也可能提供不安全范例；不能据此推定所有模型都不理解秘密或从不主动检查。仅验证正常功能，通常不足以观察未授权访问或数据外传。

GitHub 当前 push protection 覆盖受支持的合作伙伴模式、通用模式、自定义模式及处于预览的部分 AI 秘密检测；具体可用性和拦截范围依类型、计划及设置而定，不是任意秘密都能识别。

## 后果

凭据可能被不应接触它的人取得，服务受到越权调用，敏感信息扩散到日志或监控。提交到私有仓库不自动等于公开泄露，但必须按实际可见范围评估暴露并及时轮换。

## 最佳实践

1. 明确对象级授权、参数化查询、输出编码与敏感字段处理要求；为拒绝路径写检查。
2. 凭据从受控 secret 服务或环境注入，避免写入源码；环境变量和 `.gitignore` 本身不是访问隔离。
3. 配置本地检查、push protection 与入库扫描。被拦截的 push 不等于秘密从未进本地历史；绕过权限和审批也要收紧。
4. 秘密可能暴露时先撤销或轮换，再清理历史和下游副本。记录暴露范围，勿仅删除最新文件的一行。
5. 检查日志与异常内容；`log.exception` 会记录异常和堆栈，不会自动脱敏。

## 示例

```text
改之前：把完整支付异常直接返回前端，服务端也原样记录。
改之后：前端只收到通用错误和关联 ID；服务端记录经审查的最小字段，不记录令牌、完整请求体或未经清理的异常文本。
```
