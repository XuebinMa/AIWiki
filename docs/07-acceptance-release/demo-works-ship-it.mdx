> 一句话摘要：我演示了一条成功路径，不代表功能已通过发布验收。能否发布，要看事先约定的质量门槛和实际证据。

## 现象

页面能打开，理想输入能成功，你让我「看看能不能发」。我说「看起来没问题」，却没检查权限失败、数据迁移、回滚和目标环境。

## 为什么会这样

演示覆盖的条件有限，我也可能漏掉未说明的约束。一个成功截图不能证明异常路径、并发、兼容性或部署后的运行状况。Scrum 的 Definition of Done 是明确质量状态的一个例子，并不要求所有项目采用同一流程，也不让一次演示自动变成发布批准。

## 后果

用户在第一条异常路径上失败；上线后才发现环境差异；没有可执行的回退办法。口头判断还会让团队误以为已有人完成了验收。

## 最佳实践

1. 按风险写清验收标准：关键用户路径、权限、异常、数据兼容和运行要求；让每项对应检查证据或明确的未验证项。
2. 在目标环境或代表性环境验证，优先使用合成或适当脱敏的数据。不要为「真实」而把生产敏感数据带进开发会话。
3. 核对实际发布产物、配置、监控和回滚；数据迁移的回退与文件回退分别验证。
4. 我报告检查范围、结果与限制，由具备发布权限的人或受控流程作发布决定。小改动可缩小验收范围，但仍说明依据。

## 示例

```text
改之前：截图能用 → “没问题” → 发布。
改之后：关键路径通过；未测高并发；迁移与回滚已在代表环境验证；按约定风险门槛决定是否发布。
```

## 版本说明

:::note 适用范围
这是验收方法建议，不是所有模型都会漏测的实验证明。Claude Code 官方建议给出可验证的成功条件；Scrum Guide 提供了质量完成标准的具体流程示例。工具更新不代替项目自己的验收证据。
:::
