> 一句话摘要：修好 A 不代表共享代码的其他调用方仍然正常。我应检查影响范围，并用与风险相称的回归证据验证旧契约。

## 现象

我改了公共解析函数，当前页面测试通过，后台导入却失败。问题不在补丁有没有运行，而在同一函数还服务了别的输入约定。

## 为什么会这样

如果只看当前报错或 diff，我可能漏掉调用者、数据格式与异常约定。搜索和静态分析能补上下文，但动态调用、配置及跨服务依赖仍可能遗漏。测试金字塔强调不同层级互补，不给所有项目固定的测试比例，也不保证一套测试覆盖所有回归。

## 后果

旧调用方静默改变行为，兼容性问题推迟到发布后；「CI 绿了」被误当成所有依赖都检查过。

## 最佳实践

1. 找调用方、共享状态和外部契约；说明已检查与未找到的依赖，不宣称搜索结果等于完整影响图。
2. 保留修复场景，也为原有有效输入、边界和失败行为增加有意义的回归检查。
3. 测试公共实现之外的集成边界。把 CI 检查设为合并所需状态或相应保护规则，才会在合并前形成闸门。
4. 无旧调用方时可以缩减兼容性测试，但一次性迁移仍需校验数据不变量、空跑和恢复方案；持久副作用不会因「只跑一次」消失。

## 示例

```text
改之前：解析器支持新格式，默认空值处理顺手改掉，只测新页面。
改之后：先确认旧调用方的空值契约；新旧格式和错误输入都验证，明确没有覆盖的外部调用方。
```

## 版本说明

:::note 适用范围
这是变更验证方法，不是所有模型都不会搜索调用方的断言。工具、调用结构或合并规则变化时重新检查；测试通过仅支持列出的场景与环境。
:::
