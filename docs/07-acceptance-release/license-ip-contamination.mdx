> 一句话摘要：我可能输出与已有代码高度相似的片段。合并前应核对来源与许可；模型生成、扫描无命中或变量改名，都不等于权利已经清晰。

## 现象

一段实现带着特有注释、非常规命名或完整函数结构，却没有来源。我声称「原创」，但这不能证明它没有复现训练材料或检索材料。

## 为什么会这样

LiCoEval 与代码复现研究在特定模型、提示和样本上观察到高度相似输出。Carlini 等人的记忆研究也表明所测模型会逐字复现部分训练数据，但跨模型家族关系更复杂。这些是经验测量，不是侵权裁判，也不能把某个基准百分比当成所有当前输出的风险率。

**许可义务取决于具体材料及使用方式。** GPLv3 对受覆盖作品的修改、传播及源码提供有条件要求，也区分独立作品的简单聚合；AGPLv3 第 13 节还规定修改版的远程交互源码提供条件。两者都允许商业使用，不能概括为「碰到依赖就必须全产品开源」。

## 后果

来源声明或源码义务可能遗漏；客户的权利保证缺乏依据；临近发布才发现许可不兼容，返工成本上升。

## 最佳实践

1. 对特征明显、篇幅较长或影响关键交付的代码核对出处和许可，不要求我凭记忆给出处保证。
2. 记录采用的依赖、版本、许可证、通知和源码提供义务，按实际组合及发布方式评估兼容性。
3. 相似性扫描用于筛查，命中后人工核对；未命中不作无侵权保证。调整温度或改名不是合规措施。
4. 不清楚权利时使用来源明确的实现，或交给负责许可审查的人判断；简单重写不自动解除既有义务。

## 示例

```text
改之前：AI 说原创 → 删除版权头 → 合并。
改之后：保留可疑片段出处线索 → 核对许可与使用方式 → 满足义务或替换为权利清楚的实现。
```
