> 一句话摘要：我能写出看似完整的部署流程，却可能把运行、配置资源和修改权限混成一步。CI 通过不代表凭据权限正确，权限不足也不该靠全局管理员 token 补洞。

## 现象

我在 Pages 部署里加上自动启用站点，失败后让你扩大 token 权限。原本只需部署的任务，就这样附带了资源配置权限。

## 为什么会这样

GitHub Actions 的 `GITHUB_TOKEN` 权限取决于企业、组织、仓库设置及触发事件，不能一概称为默认只读。工作流或 job 一旦显式设置 `permissions`，未列出的权限会设为 `none`；还要考虑 fork PR 等事件的限制。

`actions/configure-pages` 的当前 `enablement` 功能需要另一个合适的 token，不能直接靠默认 `GITHUB_TOKEN`。其说明对 GitHub App 要求 `administration:write` **和** `pages:write`；PAT 则按其类型和文档配置。不要把当前 main 的要求默认为所有历史版本都相同。

## 后果

- 正常部署因权限不足失败，或为修复失败而引入过宽长期凭据。
- 不可信 PR、依赖脚本或 agent 输入触达了原本不需要的管理能力。
- 流程「自动化了」，却缺少谁批准首次配置、谁能改部署策略的记录。

## 最佳实践

1. 拆开一次性资源配置和日常部署。前者可人工完成，也可由独立的受信任 provisioning 流程完成；后者只保留任务必需权限。
2. 明确 workflow / job 的 `permissions`、事件、环境审批和凭据可见范围。不要只看 token 名称。
3. 固定并核对实际使用的 action 版本；完整 Pages 部署还需按部署文档配置身份令牌等权限，不是只写一个 `pages:write`。
4. 不给不可信内容管理 token。CI 中无人值守的 agent 也必须有隔离、最小凭据和输出审查。

## 示例

**改之前（反例片段）：**

```yaml
permissions: write-all
# 为了启用站点，把管理 PAT 也交给日常部署。
```

**改之后（非完整工作流）：**

```yaml
# 前提：Pages 已启用，build job 已上传 Pages artifact。
permissions: {}
jobs:
  deploy:
    needs: build
    permissions:
      contents: read
      pages: write
      id-token: write
    environment:
      name: github-pages
    steps:
      - uses: actions/deploy-pages@v4
```

这是日常部署的权限片段，没有触发器、build job 或首次站点配置；需另配受信任事件与环境保护。生产使用时按供应链策略固定经审查的 action revision。该 job 不携带管理 PAT，也不启用 configure-pages 的 enablement。

## 版本说明

:::note 适用版本
2026-10-29 核对 GitHub 权限文档和 configure-pages main 的 action.yml，部署前仍应核对固定版本。Gemini GitHub Action 的 GHSA-wpqr-6v78-jr5g 说明了历史 headless 配置信任漏洞及修复版本；它不是所有现行 CI agent 都会静默信任配置的证据。
:::
