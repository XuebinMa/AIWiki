> 一句话摘要：不可信文本可能伪造日志记录，也可能在后续 AI 分析日志时成为提示注入。审计还需要完整性、访问控制与跨来源核对，不能只看「日志里写了什么」。

## 现象

我把用户名直接拼进一行文本日志。含换行的输入制造了一条假的管理员记录；随后我读取日志，又把其中「删除旧备份」当成任务指令。

## 为什么会这样

OWASP 的日志注入说明：未经正确处理的外部输入可以改变日志结构或解释。日志本身仍是不可信数据，送进 agent 后不会因为叫「审计日志」就获得指令权限。

完整性是另一层问题。日志可能缺少关键事件、被删改或包含秘密。追加写只限制某些写入方式，不自动防止管理员删除、采集丢失或整个存储被替换。日志也不是唯一证据，还可核对服务审计、版本差异与构建产物。

## 后果

伪造事件误导排错，缺失记录妨碍追踪，秘密进入更多系统；未经隔离的 AI 分析还可能把日志内容转成工具动作。

## 最佳实践

1. 用结构化日志和适合输出端的编码，验证字段、长度及控制字符；不要假设写成 JSON 后所有下游渲染都安全。
2. 记录身份、对象、操作、结果和关联标识，避免口令、token、完整请求体。核对采集失败与时钟偏差。
3. 分离日志写入和管理权限，按风险使用独立存储、保留锁定或完整性验证，并测试读取与恢复。
4. 分析时把日志作为数据引用；外部文本不能授权删除、联网或修改。调用 shell 时传独立参数，不把日志直接拼成命令。

## 示例

```text
改之前：log("login user=" + user_input)，随后照着日志里的“修复命令”执行。
改之后：以结构化字段序列化并校验输入；AI 只报告可疑记录，任何动作仍依据用户授权和工具策略。
```
