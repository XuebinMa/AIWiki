> 一句话摘要：反复让我修改代码，并不自动累积安全性。若每轮只追功能与速度，原有安全约束可能在重构和简化中丢失。

## 现象

第一版保留鉴权、输入校验和错误处理，后续几轮「简化一下」「修到能跑」后，这些保护被删掉或换成更弱的实现。功能测试仍可能通过。

## 为什么会这样

2025 年《Security Degradation in Iterative AI Code Generation》在特定模型、任务和检测方法下观察到迭代中的安全退化。它不是所有模型每多改一轮就必然更不安全的规律。Java 安全 API 研究也显示特定 ChatGPT 任务中的误用风险，不能据此断言全部工具的当前表现。

本项目中的实践推论是：如果安全要求没有进入变更评审和验证，每次改动都可能重新破坏它。安全测试能发现其覆盖的错误；静态扫描则依赖规则和配置，两者都不覆盖所有业务安全问题。

## 后果

安全保护在后续补丁中回退；功能测试绿色掩盖了权限或敏感数据路径变化；团队把迭代次数误当成质量证据。

## 最佳实践

1. 把鉴权、敏感数据处理、密码 API 和失败策略写成可检查的不变量。
2. 修改这些路径时运行对应负向测试，检查新增、删除和被弱化的控制，而非只比较测试数量。
3. 静态扫描与依赖检查作为补充；对规则未覆盖的业务授权作人工或专项审查。
4. 无法继续验证时报告剩余风险，不用继续反复改动来替代证据。

## 示例

```text
改之前：修复请求失败 → 删除鉴权检查 → 功能恢复 → 合并。
改之后：功能恢复后仍必须通过“未授权请求被拒绝”的回归检查；若失败，修实现而非放宽安全要求。
```

## 版本说明

:::note 研究范围
引用的是已发表研究的受控设置与所测模型，不是现行所有 agent 的缺陷率。更换模型、任务、迭代策略或检测器后，需要新的证据；研究更新或安全验证流程变化时复核。
:::
