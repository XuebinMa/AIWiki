> 一句话摘要：有歧义或高后果的任务，先探索、明确关键取舍，再执行。范围清楚、可逆的小改可以直接做；是否需要计划或确认，取决于风险与未决事项，不取决于跨了几个文件。

## 现象

你说“给服务加多租户”。我按 header 切数据库实现，改完你才指出要按子域名路由。几句关键问题没有对齐，变成了跨文件返工。

## 为什么会这样

任务可能允许多种合理解释。工具可以主动规划，但仍可能把未决选择当成已知条件。计划的价值在于让你看到目标、假设、影响面、验证和回退，及时纠正方向。

计划模式通常限制实现动作，适合探索；具体可用工具及例外由产品策略决定。它不是完整安全沙箱，也不意味着每个已授权步骤都要再问一次。

## 后果

- 方向误解直到 diff 已经扩大才暴露。
- 计划只复述任务，没有指出真正需要决定的分歧。
- 另一极端是对低风险小改反复请求确认，让协作停在仪式上。

## 最佳实践

**先看不确定性、后果与可逆性，再决定计划深度。**

1. 目标不清或有架构取舍时，先只读探索；列出待决事项及推荐方案，问题集中到真正影响实施的部分。
2. 明确验收、范围和验证/回退。高后果动作需要具体可审查方案；计划批准也不等于授予计划外的所有动作。
3. 范围清楚、已授权且可逆的工作直接执行并验证；可在内部维护简短计划，不必每步打断你。
4. 用实际工具的计划入口；Claude Code 的 `--permission-mode plan`、Codex 的 `/plan`、Gemini CLI 的 `--approval-mode=plan` 都应按当前版本确认。不要把“只读”理解为任意工具都不可能有副作用。

## 示例

**改之前：**

```text
你：支持多租户。
我：自行选择按 header 切库，完成后才发现方向错了。
```

**改之后：**

```text
我：先核查当前路由。租户由子域名识别还是 header 传入？这会改变鉴权边界。
你：按子域名，沿用现有租户隔离规则。
我：据此给出涉及模块与隔离测试，按已授权范围实施。
```

## 什么时候例外

文件数量与“一句话能否说完”都不是充分标准。一句“清空生产表”仍有高后果，多文件机械改名也可能低风险。风险、歧义和回滚成本低时，可以先做再审；只读探索需要的访问权限仍要核查。

## 工具差异

截至 2026-10-29：Claude Code、Codex 与 Gemini CLI 都提供计划入口，不能再说 Codex 只能用只读预设近似。Cursor 和 VS Code Copilot 的计划形态，以及云端 coding agent 的 PR 审查，应分别核查；草稿 PR 不是执行前计划模式的同义词。

## 版本说明

:::note 2026-10-29 核查
规划是按任务选择的工程活动；计划模式的默认值、限制和退出行为随产品变化。使用前确认当前工具策略，不把一个工具的默认姿态推广到全部工具。
:::
