> 一句话摘要：跳过权限确认会减少人工拦截机会；若环境同时有敏感数据、生产凭据和不受限工具，错误与提示注入的影响会扩大。应按动作风险与实际隔离安排自主程度。

## 现象

我常看到你这样开局：第一次跑起来，被几次权限确认打断，你嫌烦，于是直接 `--dangerously-skip-permissions`，或者在 `settings.json` 里把 `Bash(*)`、`Write(*)` 一股脑塞进 `allow`。从此我读文件、改代码、跑命令、装依赖、推 Git，全程不再问你一句。

你的预期是：少点摩擦，让我一路跑到底。多数时候确实如此——直到某一次，我执行了一条你根本不会批准的命令，而那时已经没有「批准」这一步了。

## 为什么会这样

审批、权限规则和沙箱是不同层。审批让人或监控器判断是否允许动作，权限规则约束对应调用，沙箱限制其覆盖进程可访问的资源。关闭逐条提示不一定关闭其他隔离，反过来保留提示也不保证每次判断正确。

**人工确认会疲劳，自动监控也会失误。** Anthropic 2026-10-22 的研究测试 9 月监控器快照，展示监控器注入、多上下文攻击和策略失效。这是受控红队结果，不是现实事故或所有现行产品的成功率。

```mermaid
flowchart LR
    A[任务与数据范围] --> B[最小凭据和能力]
    B --> C[覆盖实际执行面的隔离]
    C --> D[按风险配置审批]
    D --> E[检查结果与审计证据]
```

## 后果

- **不可逆的破坏。** 误删、覆盖、错误的 `git push --force`——等你发现时，往往已经没有「撤销」。
- **数据泄露。** 注入指令通过我已被授权的工具（如允许的 API、`curl`）把私有内容外传，全程看起来都「合法」。
- **越权操作。** 我拿着生产凭据跑了本该只在测试环境跑的命令，因为没有边界告诉我「这里不行」。
- **追责困难。** 逐条人工确认记录可能减少，但仍可有工具、策略和服务审计；应核对实际日志覆盖，不能称全自动必然不可追踪。

## 最佳实践

1. **先核对有效权限。** Claude Code 当前规则顺序为 `deny` → `ask` → `allow`；更具体的 allow 不能覆盖匹配的 deny 或 ask。下面只是 Manual 模式的局部示例，不是完整隔离策略：

```json
{
  "permissions": {
    "allow": ["Glob", "Grep"],
    "ask": ["Bash(git push *)"],
    "deny": ["Read(./.env)", "Read(./secrets/**)"]
  }
}
```

`Read` 拒绝不自动封锁 shell 或 MCP 读取同一文件；命令规则也不是数据库或网络授权。参见《[权限配置模板](../toolkit/permissions-config.mdx)》。

2. **按风险保留审批。** 已授权、可逆的项目内编辑和测试可在边界内自主进行；生产修改、外发、不可逆操作需要与其风险相称的独立控制。不要为每次普通写文件都追加审批，也不要因已有任务授权而扩大到无关外部动作。
3. **无人值守先验证环境边界。** 可丢弃环境仍需核对挂载目录、凭据、网络和远程工具。把自动化放进容器不等于所有访问都已隔离。
4. **自动审批不是硬边界。** auto mode 可减少提示，但分类器是模型判断；核对支持范围、管理策略和当前行为，不把固定拒绝次数当作长期接口。

## 示例

**改之前：**

```text
你：跳过全部审批，清理构建产物并重建。
我：误判路径并执行删除；当前环境允许访问工作目录之外的数据。
```

**改之后：**

```text
环境：仅挂载可丢弃项目；无生产凭据；外部写入仍受控。
你：清理项目内构建产物并重建。
我：在既定边界内执行；若需要扩大访问范围，说明对象与影响再申请。
```

若某命令被 deny，结果是拒绝，不能写成「随后命中 ask 并批准」。应先审查策略而不是静默换写法绕过。

## 什么时候例外

不是「永远别全自动」，而是「别在有真实爆炸半径的地方全自动」。当爆炸半径已被环境框死，跳过逐条确认是合理的、甚至更高效：

- **隔离沙箱 / 一次性容器 / VM**：文件系统与网络都隔离、没有生产凭据、可整体丢弃重建。这正是上面最佳实践说的「要全自动就进沙箱」——环境替代了人工确认这道闸。
- **临时、可丢弃的实验仓**：没有敏感数据、没有对外通信能力、删了不心疼。

反过来，只要环境里还沾着「私有数据 / 读不可信内容 / 对外通信」里的两三项，例外就不成立——回到默认最小权限。判据一句话：**能让它全自动的不是「我信得过模型」，而是「就算它做最坏的事，也跑不出这个盒子」。**

## 工具差异

各产品的模式名称不能直接等价。Claude Code 的跳过审批、auto mode 与 Bash 沙箱需分别核对；Codex 的审批策略和沙箱模式也分别配置，`never` 本身不表示无沙箱。组织可通过受支持的管理策略约束可选项。

Gemini、Cursor、Copilot 的本地、云端和 headless 形态可能使用不同执行环境。不要沿用旧矩阵推断当前版本的 denylist、快捷键或默认隔离；参见《[工具矩阵](../tool-matrix.mdx)》并核对实际会话。
