> 一句话摘要：把生产数据交给 AI 前，先明确数据类别、获准处理方和允许用途。外部处理不自动等于公开泄露，但必须核对授权、保留、训练、驻留与审计条件。

## 现象

你让我「分析下这份用户表」「照这段内部代码改」「用这个真实配置跑一下」，然后把东西直接贴进对话或让我读真实文件。里面可能有：客户的姓名手机号、生产数据库的导出、API 密钥和凭据、尚未公开的专有源码、受监管的财务/健康数据。

我可能识别部分秘密或个人信息，但无法仅凭文本知道组织的全部授权规则。数据可能进入服务方处理、日志或缓存；是否用于训练、保留多久、能否删除，要核对具体服务、合同与设置。

## 为什么会这样

**敏感性与处理授权需要组织上下文。** 模型能识别一些 PII 或凭据格式，却不能据此完整判断业务目的、合同、法域与访问者权限。

OWASP 的 Sensitive Information Disclosure 支持数据最小化、脱敏与输出限制。经批准的外部处理方可以在合同与控制下处理相应数据；不能把所有外发、所有公开端点或所有企业服务归为同一种风险。

本条是《[默认埋漏洞 / 泄露敏感数据](../07-acceptance-release/security-data-leaks.mdx)》的上游：在读取或上传前确定允许范围，比事后仅审代码更早减少暴露。

## 后果

- 违规或超出约定的数据处理可能造成违约、隐私或商业秘密风险，是否违法取决于具体数据、处理和法域。
- 删除一段对话未必覆盖日志、备份或其他副本；反过来，也不能断言所有供应商都永久留存或用于训练。
- 未明确授权范围，会让团队无法判断哪个服务、哪个账户档位可以处理哪类资料。

## 最佳实践

- **按数据、处理方与用途分级。** 表中至少列类别、允许服务/账户、任务用途、留存要求和审批负责人；密钥等非必要数据不提供。
- **最小化与合成优先。** 给出足够诊断的结构和边界值。掩码手机号仍可能可识别；合成数据也应检查来源与重识别风险。
- **机制检查配合审查。** DLP、正则和秘密扫描只检测其覆盖的模式，仍会漏报、误报；检查失败与人工例外路径。
- **真实数据需明确授权。** 核对实际服务条款、训练使用、保留/删除、驻留、子处理方和访问控制。本地模型也要审日志、插件、网络与账户权限。

## 示例

**改之前：**

```text
你：帮我看看这条线上报错，这是出错时的完整请求日志。
   （直接贴上日志，里面含真实用户手机号、身份证号、和一个内部 API token）
我：（照单分析，这些数据已随请求发往外部模型）
后果：真实数据进入未经批准的处理链路；应评估暴露范围并按流程处理凭据。
```

**改之后：**

```text
你：帮我看看这条线上报错。（先把日志里的手机号/证件号替换成假值、token 打码）
   "phone": "SYNTHETIC_PHONE", "id": "PLACEHOLDER", "token": "<redacted>"
我：（基于结构和报错堆栈定位问题，不需要真实 PII 也能分析）
你：（核对剩余字段和堆栈无不必要的真实标识后，再提交诊断样本）
```

保留诊断所需信息，去掉不必要的真实标识；不能只遮掉一个字段就宣称已经完全匿名。

## 什么时候例外

获准的真实数据处理不是「无需边界」：本地、自托管或企业服务仍须满足相应授权与控制。公开数据也可能带有个人信息、许可和使用限制。允许范围应来自实际数据政策与服务条件，而不是「本地」「企业版」或「公开」这几个标签。

## 与相邻误区的区别

- [默认埋漏洞 / 泄露敏感数据](../07-acceptance-release/security-data-leaks.mdx)：那条是**实现层**——我写的代码把密钥写进日志、把数据返回给不该看的人；本条是**策略层**——在你决定「要不要把这类数据交给外部 AI」之前就该立的边界。一个管「代码怎么处理数据」，一个管「数据该不该到我面前」。
- [三星源码泄密给 ChatGPT（案例）](../cases/samsung-chatgpt-source-leak.mdx)：那是这条策略缺失时的**真实事故**；本条是从该类事故提炼出的**通用策略**。
- [用假占位顶替真实输入](../02-requirements/placeholder-fake-inputs.mdx)：那条里「用假数据」是我蒙混过关的反模式；本条里「用假 / 脱敏数据」是你保护真实敏感数据的正解——同一个动作，目的相反。
