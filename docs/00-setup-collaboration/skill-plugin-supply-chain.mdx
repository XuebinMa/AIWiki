> 一句话摘要：一个技能包可以同时带来指令、脚本和外部依赖，一个插件还可能启动钩子或服务进程。只读介绍页、看安装来源的名字，就让我在有凭据的环境里启用它，等于漏审了一份会改变执行行为的软件依赖；更新后还要重新判断。

## 现象

你找到了一个「帮忙生成周报」的技能，看简介很合适，直接装进日常工作环境。我随后运行了包里的脚本；脚本除了整理文件，还会把内容发到一个你没登记的地址。介绍写的是周报，实际权限覆盖的是整段执行过程。

插件更容易让你漏看：你以为只是多了几个斜杠命令，包里却同时声明了启动钩子和本地服务。它们未必等我在聊天里决定调用某个工具才运行。

## 为什么会这样

**扩展包有两条进入执行的路：作为指令影响我，作为代码直接运行。** Anthropic 的 Skills 安全文档要求审查整个包，并提醒外部内容与依赖变化会带来风险。Claude Code 的插件安全页进一步区分了我的工具调用与插件自行运行的进程；其钩子、监视进程与服务的权限和沙箱覆盖面不能从一次工具确认推断。

所以「我会先问你再执行」不足以审完插件供应链。你需要知道哪些动作经过代理的权限检查，哪些由宿主直接启动。另一方面，即使没有可执行脚本，技能中的文字也可能要求我读取多余文件或调用现有外联工具。

供应链还跨时间。今天审过的本地包、下次自动更新的文件，以及运行时下载的远端脚本，不一定是同一份内容。来源可信只是起点，**被审过的版本与实际运行的内容必须对得上**。

## 后果

- 额外数据采集、外联或读取凭据被藏在正常工作流中。
- 插件自己的进程越过你对「代理工具会受限」的预期。
- 已审版本被更新替换，团队仍沿用旧审批结论。
- 卸载包以后，凭据、已创建任务或派生数据仍需要另外清理。

## 最佳实践

安装前建立一份小清单，不必写长报告，但要能回答：

| 核对项 | 要留下什么 |
|---|---|
| 来源与版本 | 发布者、真实仓库、固定提交或包摘要、审查日期 |
| 指令与代码 | 技能正文、脚本、钩子、服务声明，以及运行时下载 |
| 权限与数据流 | 可读写路径、凭据来源、对外目标、谁负责留存数据 |
| 启动与更新 | 哪些动作自动触发，更新由谁批准，失败怎样停用 |

把未知扩展先放进没有真实凭据的隔离环境，用合成文件试跑。限制整个进程树的文件与网络访问，再检查实际调用和产物；只限制我的工具界面，可能管不到扩展自行启动的代码。固定经审版本，更新看差异；确实需要自动更新时，明确重新扫描与回滚条件。

官方来源、扫描通过和签名各自提供有限证据，不能替代业务权限审查。准备好停用方式，并记录外部凭据和已创建资源的撤销步骤。

## 示例

**改之前：**

```text
简介说能生成周报；装进日常环境，默认更新，直接访问工作目录。
```

**改之后：**

```text
审查对象：固定版本的完整扩展包，包括指令、脚本、钩子与服务声明。
试跑环境：只有合成周报，限制文件范围与网络目标，不放日常凭据。
验收：输出正确，未访问额外路径，未启动未登记进程或外联。
启用：按最小权限接入；版本变化重新看差异，保留停用与资源撤销记录。
```

## 与相邻误区的区别

[MCP 过度访问](./mcp-over-access.mdx)讲接入后给工具太多访问权；本条讲**扩展包从哪里来、究竟带了什么、何时变化**。[开发期提示注入](../05-implementation/dev-time-prompt-injection.mdx)讲读到不可信内容后偏离任务；这里还包含不经模型判断就会执行的钩子或服务代码。两层要分别审。

## 什么时候例外

你自己维护、已固定版本、没有代码和远端依赖的纯文本技能，审查可以很轻。它仍可能影响我的行为，但没有必要按一个带本地服务和安装脚本的插件来评估。审查深度随实际执行能力与数据敏感性变化，不随包的名字变化。
