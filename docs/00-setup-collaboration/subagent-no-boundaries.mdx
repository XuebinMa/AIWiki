> 一句话摘要：我可以把任务并行派给多个子代理，但上下文、消息、文件与 Git 状态是不同的共享面。明确契约、工作区和集成者；并发写优先分离工作树，共享工作区只保留一个 Git 写入者。

## 现象

你让我分派后端、前端和测试。三个子代理各自写出了合理的代码，字段却分别叫 `user_id`、`userId` 和 `id`。另一边，一个代理切了共享分支，另一个代理把提交落到了错误的 HEAD 上。文件分工没有解决接口或 Git 状态的共享。

## 为什么会这样

子代理通常有独立上下文，但并不因此拥有独立文件系统。某些形态允许消息通信或共享任务；这些能力也不会自动同步所有假设。它们需要明确的输入、契约与交接产物。

同一工作树共享 HEAD 和暂存区。提交前查询分支只能发现当时的状态，不能阻止另一个代理随后切分支。分离 Git worktree 可拆开 HEAD/index 和工作文件，但 refs、远程与部分配置仍共享；worktree 也不是安全沙箱。

## 后果

- 同一文件的并发修改冲突、接口假设不一致，集成返工。
- 暂存了其他代理的文件，或把提交放到错误分支。
- 重复调研、测试环境/端口争用、预算超支；单个代理完成不等于整体通过。

## 最佳实践

**先判断能否独立，再选择共享方式。**

1. 只读调研可以共享工作区；并发写优先使用各自 worktree/checkout。共享工作区由一个指定代理负责暂存、提交和分支操作，其他代理不得改 Git 状态。
2. 明确每个代理的文件范围、允许工具、输入版本和产出；范围指令不是沙箱，权限仍要在执行层设置。不要让“测试代理”顺手改实现或验收标准。
3. 派发前确定共享接口、字段、错误语义；共享配置与类型由指定集成者维护。消息只传必要更新，关键决定写入可核查工件。
4. 设并行数、预算、超时与无进展停止条件。集成者检查基准版本、合并冲突并运行跨模块验证，再报告整体完成。
5. Git 状态异常时先停止并发、保存 diff 和提交标识，再核查 reflog 与分支所有权。不要把强制移动或删除分支当作通用恢复步骤。

## 示例

**改之前：**

```text
你：开三个代理做后端、前端和测试，直接合起来。
我：三个代理共享目录和 Git 状态，各自猜接口、各自提交。
```

**改之后：**

```text
契约：User = { user_id: string; name: string }。
A/B：在各自工作树修改 api/ui；C：按同一契约验证，不改验收标准。
共享类型由集成者维护；共享工作区只有集成者能暂存/提交/切分支。
每个代理报告基准提交、改动、验证与阻塞；集成后再跑接口回归。
```

## 什么时候例外

各自只读的独立调研，不必创建多个 checkout。紧密依赖、同时改同一模块或协调成本很高的任务，串行可能更合适；不要为了并行而增加分工与合并工作。

## 工具差异

截至 2026-10-29：Claude Code、Codex 与 Gemini CLI 均有原生子代理文档，Cursor 也有相关能力，不能再写成只有少数工具支持。通信方式、上下文继承、默认权限与工作区隔离要分别核查。Codex 的子代理继承父级安全约束；把代理命名为“reviewer”并不会使其自动变成只读沙箱。
