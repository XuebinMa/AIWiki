> 一句话摘要：客户端权限会拦截它覆盖的调用；OS 级隔离限制相应进程实际能访问的资源。确认“哪个进程被包住、哪些路径可读、哪些网络可达”，比只看到“沙箱已开启”更重要。

## 现象

你开了内置沙箱，以为整个 agent、MCP 与 hooks 都被隔离。我运行的 shell 写不了工作区外文件，但仍可能读到主机凭据；另一条 MCP 调用还在独立服务里运行。一个开关没有代表所有执行路径。

## 为什么会这样

**客户端策略与 OS 隔离都是执行控制，但边界不同。** 前者检查匹配的工具请求；后者限制边界内进程的资源访问。把权限称为“只是建议”不准确，把 shell 沙箱当作整个 agent 的沙箱也不准确。

当前 Claude Code 文档明确：内置沙箱包住 shell 命令及其子进程；文件/网页工具、MCP、hooks 等在外面。默认读取范围仍包含主机许多位置，环境变量也可能带入凭据。因此需要分别配置读、写、网络和凭据，并检查边界外进程。

容器或 VM 可以包住更大的进程集合，但挂载、环境注入、宿主 socket 和凭据也会改变边界。工作目录隔离与只读凭据需要实际核查。

## 后果

- 被注入后，我可能从未覆盖的工具或进程访问资源。
- 写限制生效，却仍能读取敏感数据；获准出口也可能被用于外传。
- 隔离初始化失败、排除命令或批准无沙箱重试，使后续执行范围扩大。

## 最佳实践

**先画执行路径，再验证每条路径的资源范围。**

1. 列出 shell、文件工具、MCP、hooks、辅助进程的运行位置与身份。需要统一边界时，把整个 agent 及相关进程放进适当的容器/VM。
2. 只提供任务所需挂载与凭据；明确拒读敏感路径、收窄环境变量，限制网络出口。文件系统与[网络出口](./network-egress-control.mdx)要一起设计；只配一面仍有价值，但不足以覆盖完整攻击链。
3. 检查排除命令、无沙箱重试与初始化失败的处理。需要隔离作为硬要求时，失败应停止；不要默认降级继续。
4. 用无敏感数据的探针验证读、写、联网和 MCP 路径，记录实际结果。沙箱限制后果，不保证阻止[提示注入](../05-implementation/dev-time-prompt-injection.mdx)。

## 示例

**改之前：**

```text
你：沙箱已经开了，直接处理这个外部仓库。
实际：只有 shell 在边界内；MCP 有宿主权限；凭据仍被注入。
```

**改之后：**

```text
你：任务在一次性环境运行，只挂当前仓库；不提供生产凭据。
    核查 shell/MCP/hooks 都在规定边界内，外发仅限任务所需目标。
我：先用测试路径与测试目标验证限制，再开始处理资料。
```

## 什么时候例外

纯本地、可丢弃、没有敏感数据且后果有限的任务，可以采用较轻隔离；但“只读”仍可能读出秘密，“不执行代码”也可能经网页/MCP 产生外发。按可达资源和工具能力判断，见[自主性审批边界](./autonomy-approval-boundaries.mdx)。

## 工具差异

截至 2026-10-29：各工具的 CLI、IDE、本地与云端形态覆盖不同进程，默认值也会变化。不要仅按品牌比较“有/无沙箱”；逐项核查平台、读写策略、网络、MCP、hooks 与逃逸重试。Claude Code 的上述 shell 范围是本页核实的具体示例，不替其他产品作保证。
