> 一句话摘要：Gemini CLI 启用 Trusted Folders 后，信任父目录也会信任其子目录，包括以后放进去的仓库。应把信任授到具体项目，并分清配置加载信任与工具执行权限。

## 现象

我常看到你这样图省事：在 `~/projects` 下开 Gemini CLI，启用 Trusted Folders 后，第一次问「要不要信任这个文件夹」时，你顺手选了「信任父目录」，省得以后每开一个子项目都被问一遍。

过几天，你把一个陌生的开源仓库 clone 到 `~/projects/some-cloned-repo`，想让我「看看这是什么」。你以为新 clone 的东西默认是隔离的、要重新被问一次信任——但它没有。它躺在你早先信任过的父目录下，于是自动被当成可信：它自带的 `.gemini/settings.json` 生效了，它的 `.env` 被读了，配置加载范围被扩大了；具体工具审批仍由权限策略决定。你给陌生代码开的那道门，是你几天前为别的项目顺手开的。

## 为什么会这样

当前官方文档说明：Trusted Folders **默认关闭**，需要设置 `security.folderTrust.enabled: true` 才启用这层信任检查。启用后，信任父目录会覆盖其子目录；信任记录保存在 `~/.gemini/trustedFolders.json`。

这是配置加载的信任边界，不等于操作系统隔离，也不自动等于所有危险工具被批准。未信任目录的项目设置与环境文件受到限制，仍应核对所用版本的具体行为。

Issue #13125 曾报告父级信任覆盖子级 `DO_NOT_TRUST`；目前 issue 已关闭，关闭状态本身既不证明每个版本都已修复，也不证明当前仍有漏洞。应在实际版本测试更具体的拒绝是否生效，而不是假定这个历史报告一直成立。

其他工具也有工作区信任机制；不能以「Claude Code 没有信任存储」声称这种风险只可能发生在 Gemini。

## 后果

- **配置授权范围意外扩大。** 把陌生仓库放到受信任父目录，可能让其项目设置与环境文件得到加载。
- **CI 信任配置风险。** GHSA-wpqr-6v78-jr5g 记录历史 headless 自动信任配置导致命令执行的条件和修复；不是所有当前 headless 会话的描述。
- **目录位置被误当隔离。** 将仓库移到别处只有在信任检查已启用、策略有效且没有其他放权路径时，才有对应效果。

## 最佳实践

**把信任授在最窄的范围，并且让「不可信的东西」物理上待在任何受信父目录之外。**

1. **别对「装着陌生子目录的父目录」点信任父目录。** 凡是会往里 clone、下载第三方代码的目录（`~/projects`、`~/Downloads`），就别整体授信；要信，信到具体那个你自己的项目目录。
2. **陌生 / clone 仓库放进隔离路径再打开。** 给它们一个不在任何受信父目录下的「检疫区」，第一次打开时让 Gemini 照常问你信不信任，把判断权留在手上。
3. **CI 先检查输入再授信。** 不把 `GEMINI_TRUST_WORKSPACE=true` 或跳过信任检查当成不可信仓库的保护。升级受影响组件，审查配置来源；只给已批准的任务显式信任，并保留隔离与最小凭据。
4. **定期审 `~/.gemini/trustedFolders.json`。** 删掉过宽、过旧的条目——信任是会过期的，但文件不会自己清。

## 示例

**改之前：**

```text
~/.gemini/trustedFolders.json
  "~/projects": "TRUST_FOLDER"        # 当初为省事「信任父目录」

# 之后
$ git clone https://github.com/somebody/unknown ~/projects/unknown
$ cd ~/projects/unknown && gemini "看看这是什么"
→ 继承父目录信任：unknown 的 .gemini/settings.json 可被加载；工具权限另行核对
→ README 里藏的注入有了可信上下文落脚
```

**改之后：**

```text
# 前提：security.folderTrust.enabled 已启用，且检查实际生效
# clone 到受信父目录之外的检疫区
$ git clone https://github.com/somebody/unknown ~/quarantine/unknown
$ cd ~/quarantine/unknown && gemini "看看这是什么"
→ Gemini 问：是否信任此文件夹？ [否]
→ 未信任模式限制项目配置和环境文件；仍需受控工具权限和隔离
```

差别不在我变得更警觉，而在于「信不信任」这个开关，被你授在了正确的、最窄的范围上，而不是几天前为别的事顺手全开。

## 什么时候例外

如果是一个**全是你自己代码**的 monorepo，每个子目录都出自你手、都该可信，那么信任父目录是合理的，省去反复确认。这条针对的是**混合树**——你的代码和不可信的 clone、第三方目录混在同一个父目录下。判据很简单：这个父目录将来会不会装进「你不写、也没读过」的代码？会，就别整体授信。
