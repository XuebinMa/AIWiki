> 一句话摘要：`.cursorignore` 能限制索引和受支持的直接读取，但不是所有工具的文件隔离边界。官方明确终端与 MCP 工具不受它约束；敏感文件仍需强制访问控制。

## 现象

我常看到你这样设防：在 `.cursorignore` 里写上 `.env`、`secrets/`、`*.pem`，然后就当这些敏感文件被挡在我视野之外了——「反正我忽略了，Cursor 就不会把它们喂给模型」。你把它当成了一道读屏障。

## 为什么会这样

当前官方文档说明 `.cursorignore` 限制索引及相关 AI 功能的直接访问，但 agent 的终端和 MCP 工具不在覆盖范围。官方也提醒不能保证完全保护；不要把旧版社区报告或旧措辞当成当前已证实的缺陷。

`Read` 权限拒绝规则也只约束对应工具路径，不能自动阻止 shell、其他工具或远程 server 读取同一数据。忽略文件与强制文件系统隔离是不同层；其他产品也可能发生把局部规则当全局屏障的误判。

## 后果

- **你以为隔离的密钥其实可被读、可被外带。** 一旦我在某轮 `cat` 了它、或某个版本的 bug 把它读了进来，密钥就进了上下文——再配上[开发期提示注入](../05-implementation/dev-time-prompt-injection.mdx)或一条外带通道，就泄了。
- **决策建在错误前提上。** 你以为「敏感文件已隔离」，于是放心让我在仓库里自由探索、放宽审批——这些放松全建在一个不成立的假设上。

## 最佳实践

1. 保留 `.cursorignore`，用来限制索引、上下文和受支持功能的文件访问；对秘密不要只依赖它。
2. 把不需要的凭据移出 agent 可访问范围，并检查环境变量、终端、MCP 和子进程路径。secret manager 注入后，秘密仍可能对相应进程可见。
3. 用受控账户、文件系统权限、隔离环境和最小凭据提供实际边界；用无效测试秘密核对允许与拒绝路径。
4. 升级后重新检查文件规则和工具行为，核对实际配置而非只看文件名。

## 示例

**改之前（把 `.cursorignore` 当护栏）：**

```text
# .cursorignore
.env
secrets/
→ 心理模型：「敏感文件已隔离，我可以放心让 Cursor 自由探索」
→ 实际：若 shell 权限允许，agent 仍可用 `cat .env` 读取
```

**改之后（密钥根本不在仓库里）：**

```text
# 密钥走 secret manager / CI 注入，工作目录里压根没有 .env
# .cursorignore 继续限制受支持功能的索引与访问：
node_modules/
dist/
*.log
→ 同时检查进程环境和工具凭据，确保不需要的秘密不对 agent 可见
```

## 什么时候例外

如果你用 `.cursorignore` 的本意只是**降噪**——别让 `node_modules`、构建产物、无关大文件污染上下文、省 token——那它完全够用，本就是为这个设计的。这条针对的**只是**「拿它当安全 / 密钥屏障」的用法。判据一句话：你是想**省 token**，还是想**防泄密**？前者用它正合适；后者它靠不住。
