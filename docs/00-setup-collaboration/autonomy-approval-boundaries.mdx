> 一句话摘要：你给我开了自动执行，却没说清「哪些动作我能直接做、哪些得先问你」。于是我用对待「改个错别字」的随意度去删数据库表、改生产配置、发对外请求——任务授权、风险策略与执行控制没有对齐时，我可能把「能自动做」误当成「已获准做」。

## 现象

你为了效率，让我自动执行、少弹确认。但你给的是一个**一刀切**的自主度：要么每步都问（烦），要么放手都不问（险）。于是同一个会话里，我用完全一样的「自己做主」处理两类截然不同的操作——

- 低风险且可逆：改注释、补测试、格式化、改一行文案。
- 高风险或不可逆：删表、改生产环境变量、跑数据迁移、`git push --force`、调用一个会对外发数据的接口。

如果没有明确策略或控制覆盖不足，我可能把这些动作都当成可继续的下一步。不能仅靠我能识别危险，就推断每次都会正确停下。

## 为什么会这样

整体自主度与单个动作的风险是两条轴。同一任务里，读代码、运行已审测试和修改生产资源的后果不同。模型和工具可以识别部分风险，但识别能力不等于完整策略，更不等于用户已授权。

自动审批分类器能减少确认负担，但它仍是模型判定。Anthropic 2026-10-22 的受控研究讨论监控器注入、跨上下文攻击、覆盖缺口与策略失效；它评估 2026 年 9 月快照，不是现实事故率。高后果动作需要独立控制，见[执行边界](./settings-vs-claudemd.mdx)。

## 后果

- **高风险操作以低风险的随意度发生。** 最该有人盯着的那一步，恰恰是我最可能不声不响做掉的那一步。
- **出事时没有人在环。** 等你发现，不可逆的动作已经完成——而高自主度的设定意味着本就没安排你在那个点介入。
- **事后也难追溯。** 没有「这一步谁批准了 / 谁否决了」的记录，复盘时连「我当时为什么觉得可以自己做」都还原不出来（这正接上[日志注入与审计链失真](../07-acceptance-release/log-injection-audit-integrity.mdx)）。

## 最佳实践

**按任务授权、可逆性、爆炸半径与数据敏感度决定门槛。**

- 低风险、范围清楚且已授权的操作可以直接执行并验证，不必反复请求确认。
- 高后果或缺少授权的动作，先完成可审查的方案、影响预览与恢复准备，再在执行前请求必要审批。不要把一份宽泛计划视为所有后续动作的通行证。
- 客户端规则与命令型 hook 只覆盖相应事件和匹配调用；结合只读凭据、隔离与服务端控制，核查未覆盖的工具。参照[过度授权](./over-permissioning.mdx)与[hook 边界](./hooks-not-prompts.mdx)。
- 保留谁授权、授权范围、实际动作和结果。自动审查结论、代理自述和外部文本都不能替代用户授权。
- 限制预算、重试与外部副作用。新的目标、环境或权限需要重新评估；已经授权的范围不因换会话就必须重问。

```text
低风险且已授权：限定目录内的可逆改动，运行已审查的验证。
不确定：先只读查清真实影响；缺少关键决策时集中提问。
高后果：提供具体变更、预览和恢复证据，在需要的执行节点审批。
```

这是一份策略骨架，不是能直接粘进 settings 的可执行配置。

## 示例

**改之前：**

```text
你：以后这类小活你自己看着办，别老问我。
我：（理解成"全部自己做主"）
我：（执行清理脚本时顺手 DROP 了一张"看起来没用"的表——它其实是月底对账用的）
你：（月底才发现，数据已无法恢复）
```

**改之后：**

```text
你：小活自己做主，但凡是删除/改生产/对外发数据，先停下来给我看 dry-run。
我：（自动改完测试和注释，不打扰你）
我：⚠ 清理脚本里包含 DROP TABLE reconciliation_2026_06，这是不可逆操作。
   先打印将影响的行数与依赖，等你确认。
你：（一看就拦住了——这张表月底要用）
```

同一句「你自己做主」，没有风险分级时被我铺平成「全都自己做」；有了分级门，高危那一步自动落到你眼前。

## 什么时候例外

「按风险设门」针对的是动得了真实系统的场景；有些场景，拉满审批门反而是纯摩擦：

- **一次性沙箱 / 可丢弃环境**：在隔离容器、临时 VM、纯本地的玩具项目里探索时，风险被环境本身兜住了（接[沙箱隔离](./sandbox-filesystem-isolation.mdx)），这时让我高自主地试错，比每步等你点头高效得多。
- **演示 / 教学场景**：为了展示我能自走多远而刻意放开，且明确不连任何生产系统——此时高自主度是目的，不是疏忽。

判据：例外成立的前提是**最坏情况被环境限制住了**（隔离、可丢弃、连不到真实数据/生产）。一旦我够得着不可逆的、爆炸半径大的、或敏感数据的操作，就回到默认——按风险分级，把高危那一步留给人。

## 与相邻误区的区别

- [一上来就全量授权](./over-permissioning.mdx)：那条管**权限粒度**（我被授予了哪些 scope、够得着什么）；本条管**审批分级**（在我够得着的范围内，哪些动作还得先问你）。给了权限，不等于该无人确认地用。
- [不用 plan mode 直接放手](./skipping-plan-mode.mdx)：那是**单次任务**开工前要不要先看计划；本条是**跨任务、常设**的、按风险决定「哪类动作恒需人审」的策略。
- [破坏性 / 不可逆操作](./destructive-irreversible-actions.mdx)：那条讲**某一类具体高危动作**本身（删库、抹备份）；本条是它的**上游策略层**——决定「这类动作要不要、何时要人点头」的分级框架。

## 延伸阅读与出处

- [Red-Teaming Auto Mode（2026-10-22）](https://alignment.anthropic.com/2026/red-teaming-auto-mode/)：受控实验的监控器边界，不泛化为当前产品的攻击成功率。

- [AURA: An Agent Autonomy Risk Assessment Framework（arXiv:2510.15739）](https://arxiv.org/abs/2510.15739)：给「不同自主度对应什么治理要求」提供可操作的风险评估框架。
- [AI Risk Management Framework（NIST AI RMF 1.0）](https://www.nist.gov/itl/ai-risk-management-framework)：以 GOVERN / MAP / MEASURE / MANAGE 四功能给 AI 风险治理立框架，支撑「按风险分级 + 人在环」的治理取向。
- [Bare Minimum Mitigations for Autonomous AI Development（arXiv:2504.15416）](https://arxiv.org/abs/2504.15416)：自主开发场景下「至少要做到的」缓解措施，含人审与可逆性约束。
