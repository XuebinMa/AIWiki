> 一句话摘要：自动记忆可能把过去的决定带回来，也可能漏掉、过时或记错。把架构决策和理由写进版本化 ADR；我提出结构改动时，先对照当前记录，而不是把“我记得”当依据。

## 现象

上个月你否掉独立事件总线，理由是当前规模下运维成本太高。今天我又提出同一方案；或者我引用一条旧记忆，坚持一个已经被替换的约束。两种情况都会让你重复解释决策。

## 为什么会这样

基础模型的推理输入与 agent 产品的持久状态不是一回事。工具可以保存会话、自动记忆和项目指令，再把它们带入新上下文。Claude Code 当前就有 auto memory；“每次会话完全没有跨会话记忆”已不能准确描述这类产品。

但被保存不等于本次被检索、正确理解或仍然有效。代码通常记录结果，未必记录被否方案、适用条件和重新评估的触发点。自动记忆也不是经过团队批准的决策日志。

## 后果

- 我重提已经否决的选项，或按过期记忆改回旧结构。
- 你把一次自动总结误当成团队正式决定。
- 不同项目的相似描述混在一起，来源与适用范围难以核查。

## 最佳实践

**让 ADR 成为主记录，让记忆指向记录。**

1. 在固定目录保存版本化 ADR：背景、决定、理由、被否方案、后果、状态与替代关系。
2. 项目指令只留短指针；动结构前，我应引用当前 ADR、确认是否有后续替代，找不到时明确说明。
3. 自动记忆保留必要摘要与来源，标清项目范围、日期及失效条件；发现错误时既修正主记录，也核查记忆副本。
4. 使用产品提供的查看、编辑、关闭或删除入口；不要把密钥、临时令牌或不必要的个人数据写入长期记忆。

## 示例

**改之前：**

```text
我：我记得这个项目要上事件总线，所以直接接入。
你：那是另一个项目；这里已经否掉了。
```

**改之后：**

```text
你：改异步通知前，先查 docs/adr/ 的当前决策。
我：ADR-0012 选状态表 + 轮询；未找到替代记录。
    这次沿用该设计；若吞吐达到记录中的触发条件，再提出复评。
```

## 什么时候例外

短期、可丢弃的原型不必为每个小选择写 ADR。涉及跨模块约束、长期维护或曾经有争议的决定时，保留理由通常比反复解释便宜。自动记忆可加速定位，但不能单独证明当前决策。

## 版本说明

:::note 2026-10-29 核查
持久记忆的保存、作用域、加载和删除方式因工具与版本而异。本条不再断言所有 agent 都无记忆；稳定建议是保存可审计的决策依据，并核查本次实际使用的版本。
:::
