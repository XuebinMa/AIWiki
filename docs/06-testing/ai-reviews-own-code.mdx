> 一句话摘要：我的自审可以发现问题，却不能单独证明代码正确。把同会话自评、独立上下文审查和外部验证分开；不同模型也可能共享错误，审查结论要能触发、能复现、能验证。

## 现象

我刚写完权限过滤，你问“检查一下有没有 bug”。我沿用实现时的假设，漏掉跨租户访问。换个审查上下文可能发现它，也可能仍然漏掉；一句 LGTM 不能告诉你是哪一种。

## 为什么会这样

作者会话带着实现过程中的假设，容易继续沿用原来的解释。*LLM Evaluators Recognize and Favor Their Own Generations* 在所测模型和评估任务中观察到自我偏好，并研究了自我识别与偏好的关系。

这给审查独立性提供风险提示，却不能直接证明所有代码审查的盲区“完全重叠”，也不证明模型越强就必然越偏爱自己。任务、提示、上下文、工具和模型都会影响结果；同模型独立审查也可能有增量价值。

## 后果

- 自评被当成第二道独立验收，相关错误反复漏网。
- 换了模型就以为得到独立证明，忽略共同训练与类似假设。
- 为了“找出问题”而要求固定数量缺陷，制造误报和不必要改动。

## 最佳实践

**让每条审查发现附上触发场景与证据，再用外部检查验证。**

1. 按风险选择独立上下文、人审或异模型复核；不同模型不是保证，也不必为每个小改动叠加多个 reviewer。
2. 给审查者需求、diff、相关代码和调用方，见[只看 diff 的审查](./context-starved-review.mdx)；不要让作者“已经证明正确”的叙述替代事实。
3. 每条发现说明条件、影响、位置和可复现方式；没有确认的问题标为待核，不强求凑满数量。
4. 用[测试闭环](./tests-as-verification-loop.mdx)、类型检查、静态分析和必要的人审验证。测试也要检查覆盖与断言，不能用全绿代替全部验收，见[信任但要验证](./trust-then-verify.mdx)。

## 示例

**改之前：**

```text
我：权限过滤写好了。
你：自己审一下。
我：结构清晰，没问题，可以合并。
```

**改之后：**

```text
独立审查：读取权限契约、diff 与调用方，检查跨租户访问。
发现：查询遗漏 tenant_id；给出能触发的请求和测试。
修复后：运行该回归与权限测试；高风险部分由人复核。
```

## 什么时候例外

低风险、可逆小改可以先自查；在既有验证之后继续换模型，未必值得。不要提示“假设必有三个 bug”；允许无发现，并记录审查范围与尚未验证的部分。

## 工具差异

截至 2026-10-29：Claude Code 的独立审查上下文、Copilot code review、Cursor Bugbot 等产品形态要分别核查上下文与工具覆盖。另起会话能降低作者叙述的影响，却不建立统计独立性；模型与订阅可用性按实际文档确认。
