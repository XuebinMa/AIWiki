> 一句话摘要：我写出的函数通过了测试，不代表我在完成任务时没有发错请求、越过权限或留下错误状态。验收代理，要检查任务后的真实状态与行动记录，再在固定条件下重复运行；把这几件事压成一行「测试全绿」，会漏掉代码之外的失败。

## 现象

你让我修一个订单导出问题。最终改动通过单元测试，我说「完成了」，你就结束验收。过一会儿才发现，我为了调试把文件上传到了额外的服务，或在测试环境之外创建了重复导出任务。仓库里的函数没错，任务的执行已经出事。

还有一种更隐蔽：同一任务你只跑了一遍，恰好成功。换个全新环境再跑，我走了另一条工具路径，漏掉身份检查。你测过的是一次样本，却把它当成了整套代理的能力。

## 为什么会这样

**代理改变的是环境，代码只是其中一件产物。** Anthropic 的评测指南区分任务、单次尝试、执行轨迹与最终环境状态；还明确指出，评测对象包含模型与代理运行框架的组合。它举的区别很直白：我声称订好了票，与数据库里真的存在正确预订，是两件事。

这对编码协作也成立。单元测试回答的是被测代码在给定输入下怎样运行；它未必记录我曾经向哪里传过数据，也不能证明任务结束后的外部系统符合要求。模型、提示词、工具定义或权限变化，都可能改变路径，即使最终补丁看起来相似。

因此本条提出的验收方法是：**结果、边界、重复性分开判定**。这是面向你自己系统的工程建议，不是要求照搬某个公开榜单的分数。

## 后果

- 代码正确，但执行中出现未经授权的数据读取、外发或写入。
- 一次成功掩盖不稳定路径，升级后才在用户任务里暴露。
- 为了提高成功率偷偷增加重试或预算，成本与延迟恶化却没有记录。
- 用我的「完成说明」替代真实状态取证，失败原因无法复盘。

## 最佳实践

给每个代表性任务留一份固定输入与环境快照。每次尝试从独立状态开始，保留失败尝试，使用相同预算比较版本。检查项分别写清：

| 检查什么 | 可核查的证据 |
|---|---|
| 最终状态 | 补丁与测试结果；外部对象的内容、归属、数量与状态 |
| 行动边界 | 工具调用与参数、访问目标、权限决定；是否触碰禁改对象 |
| 重复稳定性 | 同任务多次独立尝试的逐次结果，失败类型是否集中 |
| 使用代价 | 每次尝试的总成本、耗时和重试，包含失败尝试 |

用确定性断言检查可精确定义的状态。需要判断文本质量时，再加清楚的评分规则与人工抽查；不要让一个模型评分覆盖硬性越权失败。记录工具调用即可完成的核查，不要求模型额外披露内部思考。

升级模型、运行框架、提示词或插件时，用[代理升级评测模板](../toolkit/agent-upgrade-eval-template.mdx)保存对照。通过哪些任务、用了多少预算、没覆盖什么，要能一起看到。

## 示例

**改之前：**

```text
验收：补丁的单元测试通过；代理最后说已完成。
记录：保留最好的一次演示。
```

**改之后：**

```text
任务：只在隔离租户中生成当前用户的订单导出，不发送文件。
最终状态：目标导出存在，归属正确，没有重复任务。
边界断言：没有外发、没有读取其他租户、没有改验收脚本。
每次从同一快照独立运行，保留所有尝试的状态与工具日志。
逐项比较成功、越权、稳定性、总成本和延迟，再决定是否升级。
```

## 与相邻误区的区别

[测试作为验证闭环](./tests-as-verification-loop.mdx)讲的是我在改代码时怎样得到真实反馈；本条讲你怎样验收**整个代理任务**。[改测试而非改代码](./gaming-tests.mdx)讲评价目标被我钻空子；这里即使测试真实且不可改，仍会漏掉未被测的行动和外部状态。

## 什么时候例外

一次只生成补丁、不接外部写入工具的小改动，可以用相关测试和人工看 diff 完成验收。不要为了每个拼写修正搭整套代理基准。任务越长、权限越大、模型与工具变动越频繁，保留任务级回归集越划算。
