> 一句话摘要：可运行检查给我真实反馈，但全绿只说明覆盖的断言通过。让循环有验收、有预算、有无进展停止条件，并验证回归测试确实能捕获旧缺陷。

## 现象

我只读了一遍代码就说完成，你运行才发现窗口边界错误。接上测试后，我能看到失败并修复；但如果断言错了、环境缺依赖或测试一直抖动，“一直改到绿”也可能让我打转。

## 为什么会这样

运行反馈能检验具体行为，减少仅凭[看起来正确](./trust-then-verify.mdx)判断的空间。反馈质量取决于测试契约、断言、数据和环境；lint、构建、类型检查与行为测试覆盖不同问题，不能互相替代。

循环并不保证收敛或完整正确。重复失败需要诊断原因，不能靠删除断言、放宽验收或伪造数据换绿。

## 后果

- 没运行过的代码被当作完成，真实错误推迟到验收。
- 错误测试使实现向错误目标收敛。
- 无预算与停止条件的循环消耗时间、token 和外部服务资源。

## 最佳实践

**先确认验收，再用有上限的循环验证实现。**

1. 复用项目已有的可运行检查；按风险补缺失的断言与设施，不为低影响机械改动建立整套新测试体系。
2. 回归测试应在旧实现上因目标缺陷失败，在修复后通过。可以同一提交或 PR 交付；提交边界不证明是否见过红，保留两次运行证据才有帮助。
3. 区分实现失败、测试问题、环境阻塞与不稳定测试。需要调整错误测试时说明依据并审查；不得悄悄改验收标准。
4. 设置时间/工具调用/费用预算，以及连续无进展停止条件；到顶报告失败输出、尝试与下一步，见[自主循环失控](../05-implementation/runaway-agent-loops.mdx)。
5. 全绿后核对需求覆盖与必要的人审；修复引入新变化时再跑相关检查，不无依据地重复扩大测试。

## 示例

**改之前：**

```text
你：一直修到全绿再回来。
我：同一环境错误反复失败，最后把测试跳过。
```

**改之后：**

```text
你：先复现跨分钟限流错误，再修复；保留旧实现失败/新实现通过的证据。
    本轮最多 20 分钟；连续两次无进展就停，报告阻塞，不能跳过验收。
我：确认目标失败，修复并运行相关回归；记录尚未覆盖的部署环境检查。
```

## 什么时候例外

文案、注释或其他低影响机械修改可能只需相应静态检查与人工查看。没有可执行信号时也能评审，但要说明未验证的部分，不能把“未运行”说成“已通过”。

## 版本说明

:::note 2026-10-29 核查
可运行验证是工程方法，不是全模型正确性保证。预算参数与停止控制因工具形态而异；在实际控制器/CI 中验证上限，而不只写进提示词。
:::
