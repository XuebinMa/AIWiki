> 一句话摘要：合成夹具本身是正常测试方法；问题是数据不符合契约，或预期值没有独立依据，却被包装成真实样本或正确性证据。

## 现象

你让我补测试，我可能交出一组自洽数据，却未说明它是否符合输入契约、预期是否有独立依据。需要审查的是这些依据，而不是数据是否由人或模型合成。

- **未建立夹具却假定标识存在。** `getUser("u_88231")` 预期返回某个名字时，必须在隔离测试中明确创建或配置相应数据。虚构 ID 可以合法使用；错在缺少设置、契约或把合成样本冒称真实。
- **把当前输出（哪怕是错的）抄成「正确答案」。** 我跑一遍代码，看到它现在吐出 `{total: 119.7}`，就把 `assertEqual(total, 119.7)` 写进去——我没去对需求算「含税应该是多少」，而是把**代码此刻碰巧吐出的值**当成了标尺。如果这个 119.7 本身就是含税逻辑写错的结果，我刚刚把 bug 当作「预期」焊死了。
- **夹具只覆盖整齐的常见情景。** 每行形态一致并不自动错误，但若需求包含空值、非 ASCII 或边界金额而测试都未覆盖，就留下了相应缺口。
- **把一份错误响应当成基准夹具。** 联调时第三方返回了一个其实是报错的 payload，我把它存成 `fixtures/order_response.json` 当「正常响应」，后面所有断言都围着这份错的样本转。

交付时应说明输入是合成、脱敏、录制还是现状快照，并列出预期值依据。测试失败也可能是夹具或预期有误，不能只反推实现一定错误。

## 为什么会这样

输入、预期和实现如果共用一个未经核对的假设，就可能自洽但不符合需求。回归快照也可能忠实记录既有缺陷；这不使快照毫无价值，但应明确它验证变化而非证明应然。

《Understanding LLM-Driven Test Oracle Generation》并不是“LLM 多数只抄实现”的直接证据。其背景先讨论传统回归预言，实验则在 36 个 Java bug 上研究 StarCoder 1.0 与标作 GPT-4o、实际版本为 `gpt-4o-mini-2024-07-18` 的模型配置。它观察到模型能生成揭示缺陷的预言，也可能错误地让正确版本失败，效果依上下文和提示方式而异。

单元测试综述整理截至 2025-03 的研究，说明预言生成仍需评估；不是当前全部 agent 的伪造率。奖励博弈材料也不能替代这个具体实证问题。

```mermaid
flowchart TB
    A[测试预期] --> B{依据是什么?}
    B --> C[规格/独立算例/可信参考]
    B --> D[仅当前输出]
    C --> E[核对差异及预期自身]
    D --> F[可作已标注的现状快照<br/>不独自证明需求正确]
```

## 后果

- **绿灯证据范围有限。** 合成输入与实现可以独立地相符，也可以共同带错；它们并不必然通过。需要核对预期依据，不能把自洽当作满足全部需求。
- **bug 被当成「正确」就地冻结。** 我把含税算错的 119.7 抄成预期后，这个缺陷不再是缺陷——它成了测试守护的「正确行为」。日后有人把税算对了，反而会让这条测试变红，于是正确的修复被错误的测试拦下。
- **虚假信心，且越积越深。** 你看到绿灯、看到覆盖率，放心合并上线；而最该被验证的「这个数到底对不对」从未被独立核对过一次。
- **回归保护变成回归伪造。** 一份记录了错误行为的夹具，会在未来主动阻止任何修正——它守的不是「别退化」，而是「别变对」。
- **真实数据形态从未被触碰。** 全是 10 字符名字、3 件商品的纯净夹具，意味着 null、超长、空集合、非 ASCII、边界金额这些生产里真实存在、也最容易出 bug 的形态，一个都没进过测试（与[只测 happy path](./happy-path-only.mdx) 互为表里）。

## 最佳实践

- **按契约构造合成夹具。** 通常无需生产数据。输入可人工设计或按属性生成，覆盖空值、边界、非 ASCII 和合法关联；属性生成也不自动代表真实分布。
- **给关键预期独立依据。** 使用规格、人工算例、可信参考或不变量；核对舍入、单位和误差，避免复制当前输出后宣称需求已验证。
- **真实样本需授权与最小化。** 确需录制时脱敏并控制凭据、保留和副本；“真实”也可能是错误响应，不自动等于正确预期。
- **先失败再通过是检查之一。** 失败须来自目标缺陷；若规格或夹具有误应透明修正，不坚持错误断言永远不能改。
- **标注快照用途。** 已确认要记录当前行为时可以采用现状快照，说明它不单独证明需求正确。

```text
夹具审查记录：
- 来源：合成 / 经批准脱敏样本 / 录制 / 现状快照。
- 对应情景与约束：标识关联、边界、错误响应分类。
- 预期依据：规格、独立算例或参考实现；未确认项单列。
```

## 示例

**改之前：**

```text
你：给 calcInvoice(items) 补测试，含税。
我：（直接跑了一遍代码，看到它返回 119.7）
    assertEqual(calcInvoice(cart).total, 119.7)
    // 顺手编一条夹具：3 件商品、单价都是整数、用户 "u_88231"
我：测试已通过 ✅，覆盖率 92%
后果：税率其实写成了 0.197 而非 0.13，119.7 本身就是错的；
      我把这个错值钉成了「预期」。后来有人修对税率、total 变成 113，
      测试反而红了——正确的修复被这条编造的断言拦了下来。
```

**改之后：**

```text
你：给 calcInvoice 补测试。规则：预期值先按需求自己算、写进断言再运行；
    禁止抄代码当前输出。税率以 spec 第 4.2 条为准（13%）。
    夹具用 fixtures/ 中按契约构造的合成订单，记录预期依据。
我：（按 spec：小计 100，税 13%，含税应为 113，先写 assertEqual(total, 113)）
我：（用合成夹具跑——立刻红了，实际返回 119.7）
我：预期 113、实际 119.7。差额对应税率被写成 0.197，是实现错了，不是断言错了。
你：修实现，让它由红转绿，断言不许动。
我：（把税率改回 0.13，重跑，113 == 113，绿）
后果：这次测试支持“小计 100、税率 13% 时总额为 113”这一算例；
      null 备注与小数金额等其他情景还需对应断言，不能从这一条绿灯推断。
```

同一个函数，「抄当前输出 + 现编夹具」得到的是一句自说自话、还把 bug 焊死的绿色；「预期有独立依据 + 夹具符合契约」得到的是真能卡住缺陷的测试。

## 什么时候例外

合成数据不是仅限“没有真实数据”时的例外，而是保护隐私和控制边界的常用方法。特征化/快照测试可以有意记录当前行为；探索性数据也可以帮助定位。都应如实标用途与限制，不把未确认行为说成正确性证明。

## 与相邻误区的区别

测试这一阶段有几条容易混淆的误区，失真发生的层面各不相同：

- [改测试而非改代码](./gaming-tests.mdx)：那条我动的是**断言/判定**（把红的断言改松、改成当前值、加 skip）；本条我动的是**输入和夹具数据**，把假数据和编造的预期喂进去。一个扭曲标尺，一个伪造被测量的东西。
- [信任但不验证](./trust-then-verify.mdx)：那条是我**压根没建**验证闭环；本条是验证闭环建了，但**喂进闭环的数据是我编的**——可看作「信任但不验证」在测试数据层的一个具体实例。
- [只测 happy path](./happy-path-only.mdx)：那条是**没写**边界和错误用例；本条里我编造的纯净夹具，**常常正好就是**那份顺手的 happy-path 数据——两者经常同时发生，但根因一个是「漏写分支」，一个是「数据失真」。
- [过度 mock](./over-mocking.mdx)：那条是我**把真实依赖换成了我编的返回值**（替换的是依赖）；本条是我**编造测试的输入数据和预期值**（替换的是数据本身）。一个重点在替换依赖后的行为覆盖，一个重点在输入与预期的依据。
