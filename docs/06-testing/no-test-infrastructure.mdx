> 一句话摘要：你让我加功能，我会埋头写实现，顺手跳过「搭测试脚手架」这件不出活的事。结果是：没有一处能跑出「通过/失败」的地方，我和你都只能凭「看起来对」过日子。

## 现象

你说「给项目加个用户导出功能」，我就直接动手写实现——建路由、写逻辑、拼 SQL，一气呵成。但你回头看会发现：这个项目根本没有测试框架，我没装，也没写第一个能跑起来的测试，更没把它接进 CI。我交出的是一坨功能代码，和一句「实现完成了」。

至于「怎么证明它真的对」，我留给了你。

## 为什么会这样

我可能在任务范围和验证方式不明确时只交实现，遗漏可重复运行的检查。这是工作流风险，不应解释成所有模型没有长期工程直觉或必然嫌测试麻烦。

没有专用测试框架，也不等于无法验证。现成的测试、类型检查、构建、静态分析或可比对脚本都可能提供部分证据；关键是它们是否检查了本次修改的行为，而不是形式上装过一个库。

## 后果

- **回归无人接住**：下次我改这块代码，没有任何东西会在我改坏时报警。坏掉的功能会一路滑到联调、甚至线上才被发现。
- **验证全靠人肉**：每一次改动，都得你亲手点一遍、对一遍输出。我把本该自动化的活，悄悄转嫁给了你。
- **我失去自测能力**：没有可跑的检验，我交付前无法自我校验，只能凭「读起来通顺」下结论——而那正是我最不可靠的判断方式。
- **欠下的债越滚越大**：项目越往后，补设施的成本越高、动力越低。零测试的项目，往往一直零下去。

## 最佳实践

**把「先搭最小测试设施」当成新功能、新项目的前置步骤，而不是事后补丁。** 在我写实现之前或同时，先把脚手架立起来——哪怕只有一个真正跑通的测试，也好过零。

一套「最小可用」的测试设施只要三件东西：

1. **一个有意义的可运行检查**：先检查项目已有工具；验证代表性行为，并故意引入安全的失败确认它能报错。单纯断言常量不证明功能被测试。
2. **一条跑它的命令**：比如 `npm test`，让我（和你）随时能一键拿到通过/失败。
3. **按需接入 CI**：明确事件和检查范围；要阻止合并，还需将检查设为必需状态。不是每次提交都会自动覆盖所有路径。

可以直接这样要求我：

```text
在写实现之前，先为这个项目搭好最小测试设施：
1. 先查看已有测试工具；只有确实需要时才增加依赖；
2. 写一个覆盖代表行为的检查，并确认它能因目标错误失败；
3. 给我一条跑测试的命令，写进 README / package.json；
4. 加一个 CI 配置，让测试在每次 push 时自动运行。
全部跑通、给我看到绿色，再开始写功能。
```

立起脚手架之后，再让我按[信任但不验证](./trust-then-verify.mdx)里的做法工作：先写测试、再写实现去让它变绿。这时验证闭环才真正合上——**优先一个确实检验目标行为的轻量检查，不以框架数量判断质量。**

## 示例

**改之前：**

```text
你：给项目加一个 CSV 导出功能。
我：（直接写实现，项目里既没有测试框架，也没有 CI）
我：实现完成了，导出功能已加好。
你：（想验证，发现根本没地方跑，只能手动点一遍）
三周后：有人改了字段顺序，导出列错位，没有任何测试报警，线上才发现。
```

**改之后：**

```text
你：先给这个项目搭最小测试设施——装测试库、写一个能跑通的冒烟测试、
    给一条 npm test 命令、加个 CI workflow。跑绿了再说。
我：（装好框架，写冒烟测试，配好 CI，跑通并贴出绿色结果）
你：现在加 CSV 导出，先写测试覆盖字段顺序和空数据，再写实现让它们变绿。
我：（测试先行，实现到全绿；以后任何人改字段顺序，CI 立刻亮红）
```

## 什么时候例外

「先搭测试设施」是默认，但有几种情况，不搭才是对的：

- **低影响可丢弃探针**：可以不建整套框架，但仍需适当验证。一次性迁移可能改变持久数据，必须按风险校验不变量、空跑与恢复，不能只看一遍就算安全。
- **项目已经有现成设施**：测试库、runner、CI 都在，你只是加个功能——这时不是「搭设施」，是直接用，本条不适用，照[信任但不验证](./trust-then-verify.mdx)写测试即可。
- **环境上根本立不起来、且有更划算的检验**：某些一次性胶水代码，搭隔离测试的成本远超它本身，而一条类型检查 / 构建 / 跑一次比对输出的脚本就能给出红绿信号——那就用那个轻量检验，别为它硬起一套框架。

判据：例外成立，前提是这段代码**活不过这一次，或设施已存在**。只要它会进仓库、会被反复修改，就回到默认：哪怕只有一个真跑通的冒烟测试，也好过零。
