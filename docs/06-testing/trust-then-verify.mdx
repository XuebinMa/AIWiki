> 一句话摘要：我交出的代码读起来很合理，你扫一眼就合并了。但「合理」是我最擅长制造的东西——它和「正确」之间，差着那些我没替你想到的边界条件。

## 现象

我给你一段实现，命名规范、结构清晰、注释到位，看上去无可挑剔。你读着觉得对，就采纳了。直到某个空输入、某个并发场景、某个超长字符串把它打穿——而那时它已经在生产环境里了。

## 为什么会这样

代码读起来合理，只说明静态阅读下没有明显问题。我可能尚未运行，也可能运行了范围不足的检查；应以实际工具结果判断，而不是断言模型从未执行代码。

Claude Code 官方建议给出可执行的成功条件。构建、测试、类型检查和人工检查各自回答不同问题：通过一项不代表其他项成立，更不证明所有输入下正确。

## 后果

- 边界条件、错误分支、并发问题被漏掉，因为它们在「读起来合理」的层面不显眼。
- 问题被推迟到更贵的阶段（联调、上线）才暴露。
- 你对我的输出建立起一种基于「文笔」的信任，而它并不可靠。

## 最佳实践

**给我一个能自己跑、能给出通过/失败信号的检验，让验证闭环自动闭合。**

最有效的形式是测试（这正是[反复纠正](../05-implementation/over-correcting.mdx)之外，对付「貌似合理」的另一道防线），但不限于测试——任何能产出「pass / fail」的东西都行：

- 一组单元测试 / 集成测试；
- 一次构建（`build`）或类型检查；
- 一个可对比的运行结果或截图。

一旦有了这样的检验，我就能进入自洽的循环：**写实现 → 跑检验 → 读结果 → 修 → 再跑**，在约定预算内修复并重跑；持续失败、环境受限或收益变小时，报告阻塞与未验证项。测试先行可以帮助验证契约，但其预期也需核对，不能保证没有漏测或错误断言。

不过检验本身也要被检验一次：**我用来宣布「通过了」的那条命令，覆盖面可能比我的改动小。** 以下两种示例说明范围错配：改了一个函数签名之后跑构建，全绿——可那条构建命令**不编译测试代码**，有个调用点没补上，跑测试才炸；另一次给一个结构体加字段后构建照样绿，因为初始化它的那处代码在一个**默认关闭的特性开关**后面，直到打开全部特性才暴露。两次的绿都是真的，只是绿的那部分不包含我改的那部分。

所以在把某条命令当成验证闭环之前，先问它一句：**我这次改动能影响到的所有代码，它都编译或执行了吗？** 测试代码、特性开关后面的分支、另一个平台的实现、示例和文档里的代码块——按风险选择受影响的测试、特性和平台，说明未覆盖项；不是每次小改动都需要穷举全部平台。

## 示例

**改之前：**

```text
你：实现一个 parsePrice(str)，把 "￥1,299.00" 解析成数字
我：（给出实现，读起来很对）
你：（直接用了）
线上：parsePrice("") 抛异常，parsePrice("1.2.3") 返回 NaN 进了账单
```

**改之后：**

```text
你：先给 parsePrice 写测试，覆盖：正常值、空串、多个小数点、负号、超大数。
我：（写出测试，其中几条立刻失败）
你：现在改实现，让所有测试通过。
我：（迭代到全绿，边界都被逼出来了）
```
