> 一句话摘要：我可能混淆写调用完成、文件完整发布与崩溃持久性，或把 watcher 当成完整操作日志；这些保证需要按 API、文件系统与发布协议分别建立。

## 现象

- **没有等待异步写入成功就读。** 我调用 writeFile 后直接读，可能读到空文件或部分内容。问题首先是调用尚未完成，不能归因于「没 fsync 所以不可见」。
- **把文件存在当成完成。** 直接创建目标路径再逐步写入时，另一个进程可能在中途读到截断 JSON。
- **把 watcher 当成一对一日志。** 即便同一 inotify 队列有序，事件合并或溢出也会使我漏掉中间变化；跨平台还存在不同语义。
- **把目录遍历当成排序。** readdir 不承诺创建顺序或字典序；先删除再创建也不是一次原子替换。

## 为什么会这样

我可能把可见性、异步完成、原子发布和崩溃持久性混成一个「写完了」。这些是不同保证：等待 writeFile 成功解决本次调用尚未完成的问题；fsync 用于持久性，**不是让普通本地文件读者看见数据的通用开关**。缓冲的用户态数据还需按所用 API 正确 flush / close。

inotify 同一个文件描述符读出的事件是有序队列，但相同未读事件可能合并，队列也可能溢出；因此有序不等于完整的操作审计日志。Node fs.watch 的平台、inode、文件名和网络文件系统限制又有所不同，不能把「所有 watcher 都乱序」写成规范。

我应从 API 和文件系统的实际保证出发，而不是以一次本地成功或对训练语料的猜测替代规范。

## 后果

读者可能消费半成品，增量处理可能漏掉变化或重复执行。问题经常依赖运行时机，普通功能测试很容易遗漏；增加重试只能掩盖症状，不能补上发布协议。

## 最佳实践

- **分清需要哪种保证。** 等待写调用成功；跨进程消费建立完成协议；崩溃持久性另按文件系统要求处理。fsync 文件后若还要求改名在崩溃后保存，通常还须同步父目录，不能只同步数据文件。
- **完整写入后再发布。** 在目标同目录创建唯一临时文件，写完并关闭，再 rename 到目标路径；发布后不再原地修改。此协议下，打开目标的读者得到完整旧版或新版。并发发布、跨文件系统与平台替换限制另作处理。
- **事件作提示，状态作依据。** debounce 后扫描对账，并处理队列溢出、重启与漏通知。若每个版本都必须消费，使用带序号的日志或队列，不能靠 watcher。
- **awaitWriteFinish 是稳定窗口启发式。** 文件尺寸一段时间不变不证明生产者已完成；需要强保证时用生产者发布协议。
- **显式排序并验证目标环境。** mtime 不是创建顺序，且可能相同；需要确定顺序时定义业务序号或稳定的排序及并列规则。

## 示例

下面是协议示意，不是可直接部署的完整错误处理实现：

```text
A: 在目标同目录创建唯一临时文件
   await 写入完整内容；检查错误；关闭
   若要求崩溃持久性：按平台要求同步文件
   rename(临时文件, 目标路径)；发布后不再原地写
   若要求改名持久性：按平台要求同步父目录
B: watcher 提醒后重新扫描；打开目标，解析并校验版本
   重复通知按版本去重；需要每一版时改用日志 / 队列
```

最小验证应覆盖写入中途读取、同目录替换、事件合并 / 溢出、生产者崩溃及每个目标 OS。通过测试只支持受测环境，不证明网络盘或所有调度都成立。

## 什么时候例外

只读取本进程已经等待写入成功的本地文件，且没有其他写者时，可以不加跨进程发布协议；是否需要崩溃持久性仍是独立问题。短脚本也要等待异步操作完成。

一次测试观察到「没有合并」不能升级为规范保证。只有可指认的 API / 文件系统契约及完整的部署前提，才足以省略对应防护。

## 与相邻误区的区别

- [并发竞态](./concurrency-races.mdx)：那条是**共享内存 / 数据库状态**上的竞态（两个执行者读改写同一份数据丢更新）；这条是**文件系统的操作与事件顺序**上的假性确定（写是否可见、事件是否有序、目录是否有顺序）。同属「把世界当顺序执行」，但战场一个在内存/DB、一个在 OS/文件系统。
- [漏掉边界分支](./missing-edge-cases.mdx)：那条是**漏了某个输入**（空数组、null、`size` 为 0）；这条不是漏输入，而是**假设文件系统本身是确定的**——即便输入全对，底层时序的非确定照样让它崩。
- [看着对但经不起边界的设计](./plausible-but-brittle-design.mdx)：这条是它的一个**具体子类**——「赌文件系统确定性」正是那种「读起来很顺、却隐含了一组真实世界不成立的健壮性前提」的脆弱假设，只不过这里的前提专指 OS / 文件系统层。
