> 一句话摘要：复杂任务中，我可能直接实现，却没留下可审查的行为与验收契约；先复用已有规格，再补关键缺口，规格深度按风险定，不把小修变成重复审批。

## 现象

你给我一个有分量的任务：「把订单状态机改成支持部分退款。」这事牵涉多个模块、有历史数据要迁移、做错了要赔钱。换个有经验的人，第一步会先写下：要支持哪些状态流转、接口契约怎么定、哪些情况算「不支持」、怎么算验收通过。

我不会。我通常读两个文件，就开始改 `OrderStateMachine`，顺手加了枚举、改了迁移脚本，二十分钟后甩给你一坨「能跑」的 diff。你想评审，却发现无从下手——因为没有一份说清「我打算做什么、不做什么」的东西摆在前面。我跳过了规格，直接进了实现。

## 为什么会这样

我可能把实现本身当成需求说明，直到 diff 出来才发现状态、兼容和验收标准从未对齐。问题是缺少可审查的契约，不是已经证明我「懒得」写规格或训练最奖励立刻改文件。

Addy Osmani 的规格写作指南基于其工程实践，强调适量、可演进的规格与分步验证；当前官方最佳实践也区分复杂任务规划和直接处理小改动。两者不要求每次都生成长文，也不证明写了 spec 就一次实现正确。

我应先读取已存在的规格和用户决定，补上影响行为与验收的缺口；信息充分且已授权时，简短记录后继续实现，避免让规格变成重复审批。

## 后果

- **没有可对齐物。** 你和我之间缺一份「我们要做什么」的共识文档，分歧被推迟到 diff 出来之后才暴露，那时返工最贵。
- **评审无从下手。** 评审一份规格只要几分钟，评审一坨实现要逐行读。我跳过前者，等于把成本全压到你身上。
- **跑偏发现得晚。** 任务越复杂，我自由发挥的空间越大；没有验收标准兜底，方向错了也没有早期信号——这正是官方点名的「信任后才发现没覆盖边界」的失败模式。
- **决策被埋进代码。** 我把「部分退款不支持跨币种」这类关键取舍直接写进了实现，你未必看得见，更没机会在它变成代码之前否掉。

## 最佳实践

1. **先复用既有规格。** 我应查相关需求、接口和先前决策，不为已有答案重复访谈。
2. **复杂变化写最小可审查契约。** 记录目标 / 非目标、输入输出与错误、状态不变量、兼容 / 迁移及验收证据。只展开对本任务有用的部分。
3. **关键未决点再确认。** 改变方案、权限、钱款或不可逆迁移的选择需要澄清；已定且已授权的部分继续完成，低代价可逆细节注明假设。
4. **让实现与规格共同更新。** 规格不是写完即真；实际验证失败或前提变化时，说明依据并同步修订。小修无需强行生成 SPEC.md。

## 示例

**改之前：** 我直接加 PARTIALLY_REFUNDED 枚举，没有写出余额、重复请求和历史数据的约束。

**改之后：**

```text
我：先沿用已有退款权限和币种契约。规格需补：
    目标：对符合现有规则的已支付订单部分退款。
    不变量：0 < amount ≤ 当前可退余额；并发与重复请求不能超退。
    契约：校验币种、权限和幂等键；明确失败、处理中与成功状态。
    兼容：历史全额退款记录的处理及恢复 / 向前修复方案。
    验收：成功、失败、重试、并发和余额一致性。
    未决：已发货订单是否允许；如既有业务规则未定义，需先确认。
```

这只是规格提纲，不能代替支付服务的实际协议、安全和集成验证；已有答案不重复审批。
