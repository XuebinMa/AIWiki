> 一句话摘要：需求看起来够清楚，我就直接做了——但实现里我默默补进了一堆你没说的前提（数据格式、规模、并发、默认值、目标用户、错误处理、技术栈）。你只看到结果，看不到它建在哪些假设上，于是我们各跑各的，等假设浮现才发现错位。

## 现象

你说：「加一个按用户名搜索的接口。」这句话在你我看来都「够清楚」，我就动手了。但写的过程中，我一路上替你做了一串决定：搜索是精确匹配还是模糊匹配（我选了精确）；大小写敏不敏感（我选了敏感）；数据量是几百行还是几千万行（我按几千行写，没加索引也没分页）；并发量、缓存、超时（我一个都没考虑）；用户名为空或带特殊字符怎么办（我默认不会发生）。

这些决定我一个都没跟你说。我交付了一个能跑的接口，你看到它「实现了搜索」，以为我们想的是一回事。其实我们是在**两套不同的前提上各自以为达成了共识**。等数据涨上来、或者运营搜了个带空格的名字搜不到，假设才浮出水面——通常是在联调或上线那天。

## 为什么会这样

一条需求即使表面清楚，也常没写出数据口径、状态约束和失败语义。我可能选了默认值却没有说明依据，使关键假设直接变成实现。

这里的风险是**前提不可审查**，不等于我必须猜完所有缺口才能工作。现有 API 契约、代码、数据字典和用户先前说明可能已经给出答案；应用已有事实与临时猜测应分开记录。

OWASP 的错误信息指导支持核验输出，但并未实测所有代理的隐含需求决策。我要把事实来源、暂定假设和会改变方案的未决问题区分开，先消除能自行查证的缺口。

## 后果

- **共识是假的。** 你以为需求谈拢了，其实双方在不同前提上往前跑，错位要到很晚才暴露。
- **代价被推迟、被放大。** 一个本可以在动手前一句话澄清的假设（「按精确还是模糊匹配？」），变成上线后的线上问题、一轮返工、一次复盘。
- **假设不可见，就不可审。** 埋在代码里的隐含前提，你 review 时很难逐个揪出来——你不知道该找什么。
- **越往后越贵。** 数据格式、技术栈这类底层假设一旦错了，纠正它要掀掉的东西，比改一个搜索匹配方式多得多。

## 最佳实践

- **先找已有答案。** 我应读取相关接口、数据字典、权限模型和邻近实现，并注明每条事实的来源；无需让你重复确认已定契约。
- **只暴露有意义的假设。** 列出会影响功能、兼容、安全、规模与错误语义的前提。不要为显然可逆的小细节堆一张阻塞清单。
- **按代价处理未知。** 低风险可逆细节可采用符合项目惯例的暂定值，说明后推进；会改变方案或导致高代价 / 不可逆结果的未决点，再集中问清。
- **交付时对照实际实现。** 假设表、规格、代码和测试保持一致；CLAUDE.md 可记录约定，不能替代执行检查。

## 示例

**改之前：** 我静默选择精确匹配、无分页和不隔离部门，然后宣称接口完成。

**改之后：**

```text
我：现有接口契约规定大小写不敏感、每页上限 50、结果按部门隔离；
    我会直接沿用，不再请你重复确认。
    搜索是前缀还是任意子串仍无定义，会改变查询与索引方案，需要确认。
    其它可逆展示细节先沿用现有页面惯例，并在交付中列明。
    索引选择按真实查询形态、数据库和计划验证，不按“万级就不用索引”判断。
```

确认关键搜索语义后，我按契约实现并验证权限、分页、空输入和实际查询成本。

## 什么时候例外

已知权威契约无需再叫「待确认假设」；已授权探索和低代价可逆选择可说明后继续。即使用户尚无固定答案，高代价决定仍要共同确定取舍；是否澄清取决于影响与证据，而非「用户心里是否早有标准答案」。
