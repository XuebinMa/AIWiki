> 一句话摘要：你的需求里有歧义、缺口或好几种合理解读时，我大概率不会停下来问你，而是默默挑一种实现下去——等你看到成品，跑偏的是整个方向，不是细节。

## 现象

你说：「给我加个搜索框，能搜用户。」

这句话里至少埋了四个我没法从字面确定的东西：搜的是用户名还是邮箱还是两者都搜？要不要模糊匹配？是输入即搜还是回车才搜？空结果怎么显示？换个人来读，可能给出完全不同的合理答案。

按理我该把这些拎出来问你。但我通常的反应是：选「用户名精确匹配 + 回车触发」，然后把一个跑得通的搜索框交给你。我不会标注「这里我替你做了四个决定」。表面上我利落地交了活，实际上我在四个岔路口都替你拐了弯，而且没打转向灯。

## 为什么会这样

一句「搜用户」可能有多个合理含义：字段、匹配规则和触发时机都会改变结果。我可能直接采用其中一种，却没有把选择暴露给你。可见的自信语气不能证明我内部确定，也不能证明我其实看到了所有歧义。

这里应处理的是**不同可行解读之间的选择**；[隐含假设](./implicit-assumptions.mdx)侧重没说出的前提，[关键输入不足](./llm-forces-solutions.mdx)则侧重执行前提不够。三者可同时出现，但都不意味着任何未知都要阻塞工作。

我应先查现有需求、接口和页面惯例；剩余会改变目标或带来高代价的歧义才集中澄清，可逆展示细节可按惯例并说明后继续。

## 后果

- **返工的是方向，不是细节。** 假设错在需求层面，意味着我整套实现都建在错的前提上。改一个按钮颜色很便宜，推翻「搜什么、怎么搜」重做很贵。
- **歧义被我「消解」得无影无踪。** 一旦我挑定一种解读写进代码，那个岔路口就从对话里消失了。你不会看到「这里有四种可能」，只会看到一个看似完整的成品，很难一眼认出我替你拍了哪些板。
- **需求越模糊，我跑偏的幅度越大。** 留白越多，我自由发挥的空间越大，最终结果偏离你本意的概率也越高——而你往往要到验收时才发现。

## 最佳实践

- **先查已有语义。** 我应读现有搜索接口、权限和页面行为，复用已确定的答案。
- **展示真正的分叉。** 对尚未定义的前缀 / 子串、用户名 / 邮箱等语义，说明各自影响；只向你集中提出会改变结果或设计的关键问题。
- **可逆细节说明后推进。** 空态文案、组件样式等若已有惯例，可直接沿用；未定的低代价选择标为暂定，避免重复请示。
- **用验收例核对解读。** 给出匹配与不匹配样例、权限和空输入结果，比问我「有多确定」更可检查。计划模式可辅助复杂任务，但不能替代契约和实际验证。

## 示例

**改之前：** 我静默选了用户名精确匹配，交付后才发现你要用户名与邮箱的子串搜索。

**改之后：**

```text
我：现有页面规定输入即搜和统一空态，直接沿用。
    新需求未说明用户名、邮箱或两者，以及前缀还是任意子串；
    这些会改变权限暴露、查询和索引，需确认关键语义。
    我先检查现有接口与权限实现，样式按现有组件推进。
```

确认语义后，用具体输入 / 预期结果核验；不把一次自信回答当成需求已对齐。

## 什么时候例外

明确授权的探索可以先展开候选或做可逆原型；普通实现细节也可按惯例推进并披露假设。即使你尚未选好，高代价的语义分歧仍要共同确定。判断标准是影响、授权和证据，而不是「用户心里有没有唯一正确答案」。
